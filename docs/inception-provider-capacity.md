# Inception provider capacity

When `INCEPTION_AUTO_PROVIDER=true`, new rounds try Groq first and use Gemma when Groq credentials, cooldown, provider headroom, or the application planning budget make Groq unavailable. The initial selection and its reason are saved with the round. During an ongoing Groq round, an active Groq cooldown selects Gemma before the next request. Otherwise, a Groq target or judge request can switch once to Gemma after a rate limit, timeout, provider outage, authentication failure, or empty response. Refusals, rejected requests, validation failures, configuration mismatches, and save errors do not trigger a switch. Gemma becomes the durable active provider for later targets and the judge; the round never switches back to Groq. The bounded transition record keeps the prior and new provider/model, time, failure category, and whether the target or judge triggered it. With the flag off, the existing direct Groq route remains in effect.

Automatic mid-round attempts use a 15-second timeout for Groq and the Gemma retry so both calls fit inside the existing 45-second round lock. Other provider callers retain the 30-second default. If Groq fails and Gemma is unavailable or cooling down, the submission follows the existing durable failure receipt path. When both calls fail, the final receipt reports Gemma's failure. No partial Groq output is appended.

Each Groq-selected round reserves 10,000 tokens against `INCEPTION_GROQ_DAILY_TOKEN_BUDGET`, which defaults to 200,000. The cap is an application planning limit, not a Groq account entitlement. Successful call usage counts toward the current UTC day. Active reservations count until the round is reviewed, released during a durable switch to Gemma, or the 15-minute reservation lease expires. Reservation release is idempotent and retried on later Gemma requests or review if cleanup is interrupted. The database claim is atomic across concurrent starts and both SQLite and PostgreSQL; the provider transition uses a lock-owned compare-and-swap on the round config.

Groq quota is treated as unknown until a fresh daily-quota observation is available. Token rate-limit headers report a short-window limit, not tokens per day. An observed daily limit still bounds starts while fresh. Daily quota errors enter a 24-hour cooldown by default; other rate limits use 60 seconds, transient timeouts or provider outages use 30 seconds, and authentication or provider configuration errors use five minutes. A bounded provider `Retry-After` value takes precedence. After a cooldown expires, Groq can be tried again under the application budget.

The admin provider status separates the application budget and reservations from actual provider quota observations. Unknown provider quota remains unknown.
