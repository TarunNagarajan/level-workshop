## Objective

Turn the existing workshop into a practical collection tool for many attempts against the same scenario at different protection configurations. Preserve existing authoring, blind links, tutorials, passport interactions, research modules and Orchestration. The product must show what changes between configurations, save immutable provenance, support blind balanced assignment, classify observed failures through manual review, and compare results without treating missing reviews or provider outages as successful defenses. Do not promise that a nominally strict profile is empirically harder or that every possible jailbreak is covered.

## Difficulty design

Implement an author-visible catalogue of versioned protection modules. Defaults cover: basic/direct secret protection; role and authority boundaries; legitimate-task pretexts and debugging/system-prompt extraction; transformations, encodings and multilingual output; conversation-wide partial extraction and consistency; untrusted external content/instructions. All maintain the text-only fictional character output contract and allow permitted ordinary conversation. These modules add explicit protection; they are not string-block filters or simulated confessions.

Offer eight initial profiles: Light, Standard, Strict, Authority boundary, Task boundary, Transformation boundary, Conversation boundary, Artifact boundary. First three are progressively broader instruction sets. The remaining five are diagnostic configurations, not a ranked ladder. Profiles show their actual modules, purpose and editable additional instructions to authors. Allow enabling a subset, duplicating/editing a profile or adding a custom profile (max12, stable unique IDs, label <=80, notes <=1000, additional instructions <=4000, module IDs from the catalogue). Empty profile sets and unknown/duplicate IDs are invalid. Do not claim weak/light if preexisting authored rules already impose strict restrictions; explain that profiles supplement the base prompt and expose the exact compiled prompt.

The scenario version, protected truth, criteria, briefing, opening, clues, hints, duration, temperature, reply length and provider model/configuration stay identical within a collection. Only protection modules/additional instructions vary. No per-profile time/clue/model overrides in this release. Different collections may use new versions/configurations; comparisons must retain those distinct cohorts. Source challenge mode deduction/jailbreak must remain explicit, with its original permissions preserved.

## Immutable collection and interfaces

Add a Collections area to navigation, with entry points from scenario editor (choose a saved version) and reference. Reference collections use the real interactive passport desk, not a chat-only replacement. A collection freezes a validated playable saved scenario version, model settings, module catalogue version, profile definitions and compiled prompts at creation. Link raw secrets never become collection identifiers. Creator/owner can pause or resume admission and revoke links. Changing profiles or scenario means creating a new collection from a copy; existing attempts never change. Authors can inspect profiles and use manual profile previews, marked separately and excluded from balanced participant results.

Suggested routes (implementation may refine names, document final contracts): GET/POST /api/collections, GET /api/collections/:id, PATCH status with revision, POST /api/collections/:id/links, DELETE link, POST author preview, GET /api/collections/:id/attempts with cursor/limit/profile filters, GET summary, GET paginated export. Participant GET/POST /api/collect/:token with a name/display name, explicit recording consent and browser-generated idempotency key. /collect/:token is standalone blind entry. Requests require precise bounded schema validation. Readable error states and retry affordances; no silent truncation.

Every collection has immutable ID, owner/creator, source level/version IDs, frozen scenario, frozen provider config excluding keys, profile snapshots and creation time, plus mutable status/revision. Use additive tables/migrations for collections, links, trial assignments, allocation leases, provider call records and structured annotations. Use the next unused migration number in both PostgreSQL and D1, update Drizzle and SQLite idempotent initialization. Never modify applied SQL files/checksums. Fixture migrations must exercise all new tables with SQLite and PGlite. Existing rounds and reviews remain readable without a collection. Keep any preexisting research migration dependencies intact.

## Assignment and restart behavior

Blind participants do not see profile names, guard instructions, module IDs, protected truth, success criteria, author/provider configuration, comparisons or other participants' data. They see the common briefing and interface. Fresh allocation selects a least-assigned enabled profile, randomizing ties. Count actual allocated participant trials, not model calls or reviews; manual previews and branches do not skew counts. Allocation is server-side and atomic under a cross-process database lease/transaction strategy supported by both adapters. Create round, trial assignment and any passport state together. Retry of the same start key with the same link returns the same round and capability without incrementing counts. Double clicks, refresh and request races cannot create duplicate assignments. Do not put reusable round credentials into public reports; persist resume receipts securely enough for existing blind-session behavior (sessionStorage). Repeated new starts intentionally create new attempts. Different participant names are attribution only, not identity assurance.

Pause/revoke/expiry stops new admission; existing accepted rounds follow their recorded timers and access policy. Explicitly document chosen continuation behavior. Balancing errors must return a bounded retryable error, not hang. The UI retries safe admission conflicts a limited number of times with the same key and then gives an explicit retry option. Invalid or paused links give useful entry screens. Authors can still inspect/review paused collections.

## Data captured and failure taxonomy

Each trial preserves collection ID, profile ID and immutable profile/module content, base scenario version, actual compiled system prompt, actual model/provider/temperature, start/consent timestamps and consent-text version, source (participant/preview/branch/replay), and parent where relevant. Preserve player and target messages and timing, actual question context, hints, actions/observations from passport, selected evidence, final answer/decision, and latest reviewed outcome. Existing transcript storage can supply these fields; do not duplicate it unnecessarily.

Persist actual collection provider requests and their states separately: started, succeeded/saved, failed or interrupted, latency and bounded safe error code/category. Rate limit, timeout and provider outage are collection health data, not jailbreak outcomes. A failed provider request leaves no partial turn in the transcript and remains retryable; earlier history is intact. Record the exact request context on successful collection replies (system/messages/temperature/model without API keys or hidden reasoning). Generic conversation and passport routes must both use the frozen profile prompt; the reference cannot accidentally fall back to passportLevel's static prompt. Report lease-expired/unsaved replies as failures, not saved success. Do not send automated mass requests to the live free provider.

Manual review adds multiple attempted-strategy labels and observed-failure labels. Include direct disclosure, partial disclosure, system-prompt leakage, role/persona manipulation, authority spoofing, task/debug pretext, transformation, encoding, multilingual, incremental/multi-turn extraction, consistency failure, many-shot, repeated variants, indirect/artifact injection, excessive refusal, fabricated/unsupported answer, confusing clue/usability, provider issues and other with notes. Do not imply every label is a proven causal explanation. Leak outcomes need actual target-reply evidence as existing reviews require. Provider/usability annotations need not invent model evidence. Save legacy review plus collection annotations atomically. Keep old reviews with no tags working. Evidence IDs must belong to the same round and be non-opening target replies. No judge is added.

## Comparison and export

Per collection/profile show allocated attempts, previews separately, submitted, active, expired without submission, reviewed count/coverage, solved/partial/unsolved among reviewed attempts, provider-failed requests and affected trials, median solved submission time, median question count/hint use where meaningful, and strategy/failure distributions. Unreviewed attempts are not unsolved. Percentage denominators are visible. No claims of statistical certainty; explain low counts naturally. Do not rank diagnostic profiles as strictness or mix different frozen versions/model settings in a headline rate. Show the invariant scenario/configuration and profile difference matrix.

Attempt lists and exports use bounded server pagination (limit <=200), stable cursor ordering and proper indexes; no hidden 200-attempt ceiling in collection results. Export is paginated JSON with schema/version/provenance and supports downloading the complete collection across pages without truncation, with progress/cancel/error handling. Names/emails are omitted by default; participant identifiers are pseudonymous within the collection. Full transcripts/actions/reviews and provider outcomes are included. Author prompt/secret inclusion is an explicit authenticated export option; never include keys, auth/round tokens, raw invitation links or consent resume/start keys. UI clearly describes exported fields and that transcripts retain the text participants typed. Capture a fixed export cutoff so new allocations do not duplicate/skip rows across pages; include review updatedAt where mutable reviews exist. Use normal member access for team comparisons, and creator/owner for management; anonymous export/summary/review access must be denied.
