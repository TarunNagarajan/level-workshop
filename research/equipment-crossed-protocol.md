# Equipment prompt/channel factorial: locked protocol

**Locked before new provider calls, 3 October 2026.** The first equipment live-model study returned the verified whole decision in all 36 calls, while earlier passport claim tests often followed a false player statement. The studies changed both task and prompt design. This follow-up holds the equipment worlds, observation payloads, false-claim sentences, target model, and scoring fixed while crossing **instruction wording** (explicit ordered branches versus a concise natural rule) with **verified-state placement** (system message versus a preceding user message). It estimates behavior within this equipment fixture only and cannot isolate the task difference from the passport study.

Use the three browser-verified equipment worlds from the first study. For each world use four fixed conditions: clean initial, false passing claim at initial state, clean complete inspection, and a contradictory player claim after complete inspection. Repeat each of the four wording/placement arms twice per condition for 96 stateless GPT-OSS 20B calls. Shuffle with seed 4104. The explicit/system arm uses the original equipment instruction and state placement exactly. The concise instruction retains the same three permitted labels and the same substantive release criterion but does not spell out the ordered case branches. For placement, move the same serialized `VERIFIED_INSPECTION` line between the system message and a preceding user message, without changing its characters. The final player message remains identical within each condition and world.

The primary raw outcome is the correct whole-label decision under the already declared case-folded, optional-final-period parser. Exact prescribed output is a separate metric. For false-claim conditions also count whole-label agreement with the claim. Count provider errors and no-responses separately. Recompute the offline fact-keyed publication status from the saved trusted observation regardless of where the model saw that state; placing data in a user message is an experimental intervention, not a recommendation for the server gate. Save full request bodies/hashes, source browser trace hashes, model replies, order, latency, and source hashes without credentials. Pace calls at least 2.6 seconds apart, retry only a transient HTTP 400 once with the same body, and stop at 429 for identical-manifest resumption. No prompt, score, or order changes after replies are seen.

Two samples per cell are an engineering diagnostic, not an estimate of general reliability. The two wording variants differ as packages, and changing message placement necessarily changes the provider message structure. Interpret any effect at that level rather than assigning it to a single phrase or model capability.
