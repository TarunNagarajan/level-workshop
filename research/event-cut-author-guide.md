# Designing an interaction that actually matters

An author starts with one question the player must answer, two plausible worlds with different correct answers, and one action the player is meant to perform. For example, two travel documents may look ordinary when closed, but comparing their security seals reveals whether they belong together. The author should be able to say exactly what becomes visible after `compare-seals` and why that observation changes the next question or decision.

The scene contract records every action available to the player, what each action changes, and the complete observation returned after it. An observation includes the rendered object text, accessible names, action responses, initial and later API payloads, and any facts given to the target model. If moving an item, asking a question, or inspecting a second object can reveal the same world-specific fact, that path belongs in the model. A designer should not omit an inconvenient action from the graph simply to obtain a pass.

The [event-cut auditor](event-cut-contract.mjs) runs both worlds through the same action sequences. It checks whether the observations and available actions stay identical on every sequence that avoids the declared action. A pass means the action lies on every distinguishing path *within this modeled scene*, and the auditor supplies one path showing that the action can reveal something useful. A failure gives the shortest alternate path and the first differing field. An exhausted state limit produces an inconclusive result. The [tests](event-cut-contract.test.mjs) show a valid comparison, an alternate `inspect-seal` bypass, a leak through action availability, a delayed reveal, and invalid state handling.

The author uses the bypass path as a design note. If `inspect-seal` reveals the answer before comparison, the level can make that inspection show only a partial clue, or declare that both actions are valid routes to the insight. If the initial API response already includes the hidden field, the server should delay that field until the corresponding event. If an action is available only in one world, the interface may need to show it in both and produce a neutral response where it has no effect. The aim is a believable interaction, not forcing a particular click order.

When more than one interaction is deliberately valid, the auditor can search for inclusion-minimal **sets** of actions that cover every distinguishing path. In the badge example, both comparing the seals and directly inspecting a seal can reveal the answer, so neither action alone is necessary. The tool can certify the set containing both, and may find another set involving a prerequisite such as opening the ticket. These are structural facts about the scene, not recommendations to make every action mandatory. The author chooses which paths fit the story and the time limit.

For the sandbox implementation, compile the graph from the same server reducer and serializers used by real sessions. Store the two world bindings server-side, replay the shortest failure path in the author preview, and show the exact differing field beside the object. Recompute the certificate when actions, content, accessibility labels, API response shapes, or model context change. This audit establishes an information dependency. It cannot establish that a human will discover the object in three to five minutes or that a target model will disclose its private truth. Pair it with a short human playtest and the separate model-behavior audit in [the research article](counterfactual-handoff-contracts.md).
