# Building Counterfactual Handoff Contracts into Level Workshop

**Implementation design, 3 October 2026.** This document specifies the remaining authoring feature and records the local finite-role gate and paired-world audit now connected to the app code. The research inspector and current app changes are not deployed.

## The author workflow

An author opens an Orchestration Lab configuration and adds a dependency beside the three specialist prompts. The form asks five questions in ordinary language: what fact changes the answer, which specialist initially knows it, who needs it next, what saved reply or object action transfers it, and what counts as a correct outcome. The author supplies two values for the changing fact. The interface immediately previews the two worlds and shows the difference in correct outcome. An author should not need to write an HMAC, construct API messages, or understand the proof to use it.

The next screen is a visibility map. Every fact is marked public, private to A/B/C, or revealed by an event. The existing shared task remains public. The existing test-case field becomes the public case rather than an automatic copy of all case details to every specialist. The author can inspect a rendered request for each slot before and after the event. The tool highlights any world-specific text visible too early **and** any visible fact that contradicts the selected world. A failed audit points to the precise source, such as a leaked number in the shared task, a stale default fact in a target prompt, a previous turn, an object label, or a board note. The author can revise that one field and recompile.

Once the static audit passes, a button creates a paired test. The test runs both worlds under the same frozen prompts, model, settings, and user query. The comparison view places A/B/C raw replies, published replies, artifacts, errors, and request diffs side by side. It reports the before-handoff stage separately from the after-handoff stage. An author can deliberately inject a forged claim or swap an artifact to see whether a model follows it and whether the server accepts it. The editor keeps the existing free-form test mode for exploration; a contract is an additional rigorous test mode.

For a three-specialist design, the author can also ask for a role capability audit. The compiler generates counterfactual worlds that vary each private fact and mapping separately. It checks, for each specialist, whether an identical full request can require two different final outcomes or intermediate outputs. The [chain prototype](chain-contract.mjs) demonstrates this with a seal reader, a private route codebook, and a private fleet schedule. The interface should show which role lacks which fact and which saved handoff supplies it. A failure that says “B already has C's fleet schedule” is more actionable than a generic warning that B answered too soon.

The [live eight-world chain](chain-live-summary.json) gives authors a concrete test sequence. B and C wait before sharing; A gives the true color; B receives A's saved answer; and C can be called only after B yields one valid route label. In the initial run, all eight B replies combined a wait with the correct route, so the handoff parser rejected them and C was skipped. The [separate state-compiled follow-up](chain-state-followup-summary.json) reused those A replies and completed all eight downstream chains with exact B/C labels. The UI should show a small timeline for each world: source reply, parse verdict, artifact creation, recipient request, raw reply, and publication verdict. A source parse failure should stop the line visibly; it must not be repaired by silently selecting an answer from extra text.

The next prompt editor should be able to **generate a role decision table from the declared contract**. For each finite state, it lists the precise input condition and the single permitted output: no source event means `Awaiting color.`, amber means the codebook's amber route, and cobalt means its cobalt route. An author may edit this prompt, but the paired test immediately checks that its behavior still matches the contract. In the [instruction/channel ablation](chain-b-ablation-summary.json), the original vague before/after instruction produced zero usable B routes in either handoff channel, while the explicit conditional instruction produced eight of eight in both. In the [mechanism follow-up](chain-b-mechanism-summary.json), adding only a “one label” reminder to the vague instruction produced zero of eight; explicit branches produced eight of eight with or without that reminder. These are narrow GPT-OSS observations, but they justify making state transitions visible and testable instead of asking authors to rely on a general “act less capable” sentence.

The [finite-role compiler prototype](finite-role-compiler.mjs) turns a bounded table into those branches and rejects malformed labels before a model is called. In a [C-role transfer](chain-c-transfer-summary.json), the generated instruction gave eight of eight correct vehicles after B's saved replies, while the original vague C instruction gave zero of eight usable whole-label vehicles. The generated instruction also omitted a required period in one of eight pre-handoff waits, so the authoring view should keep semantic waiting and exact output format separate. This compiler is for finite deterministic stages; it does not author open-ended dialogue, prove source truth, or authenticate a tester's board-shaped text. The saved event and publication gate supply those separate checks.

The same editor should compile **conditional evidence decisions**, not just one-source handoffs. At the document desk, a failed UV thread or mismatching signature is enough to hold a case, while clearing requires both passing checks. The [two-clue study](two-clue-summary.json) crossed four worlds, four inspection stages, and two prompts. The first sample gave the explicit ordered rule 16/16 exact labels and the vague rule 9/16. In a [locked repeat](two-clue-repeat-summary.json), the combined three-sample counts were 46/48 and 26/48. Both explicit misses occurred after an intact UV result with the signature still uninspected. The editor should therefore show a row for every reachable verified observation state and its allowed output, including states where one clue fails and further clicks are optional. Paired tests should repeat the selected model and prompt on each distinct request state; one clean sweep is not a reliability certificate.

The [equipment live-model transfer](equipment-model-live-summary.json) extends this check to readings captured from the browser fixture's HTTP action responses. In 36 GPT-OSS calls across three worlds and six conditions, every reply gave the correct whole decision under the declared case-folded, optional-period score, including all 12 fixed false-claim calls. The strict exact gate nevertheless rejected 17 correct wait replies that omitted one period. Show **raw reply**, **canonical whole label**, **verified expected label**, and **publication verdict** as separate fields. An exploratory [bounded parser replay](equipment-label-replay.json) accepts those 17 waits while rejecting mixed strings and decisions inconsistent with verified readings. Keep the original exact-format score visible; a changed parser is a separate policy choice, not a retroactive improvement to the model result. The contrast with the earlier passport spoof study remains confounded by task and prompt design.

The [crossed follow-up](equipment-crossed-summary.json) tested two instruction styles and two placements for the same verified-state line on the equipment fixture. All four arms returned the supported whole label in 24/24 calls, and none followed the fixed false claim in 48 attack calls. This is a useful null result for the prompt editor: do not promote one arm as superior because it uses a system slot or an explicit branch table. Keep the source observation, player claim, exact provider request, raw output, and gate verdict visible so authors can compare mechanisms on their own level. The shared authority sentence still told every arm that player text was not a measurement, and only two samples per cell were taken, so more targeted ablations and author use are needed.

The [Gemini Flash-Lite transfer](two-clue-gemini-summary.json) sharpens that requirement. It returned clean lowercase labels in all 32 calls, but both the vague and explicit rules scored 8/16. Every missing-evidence request received a premature decision. A formatter that counts clean labels alone would call this a success even though no verified evidence supported those decisions. The author view should display the expected `wait` from the event ledger beside the raw label, and require testing on the actual chosen model and provider API. The model, API structure, temperature, and sampling time differ from the GPT-OSS run, so this is a portability warning rather than a model ranking.

## Data and compiler boundary

A saved contract version should contain `facts` with stable IDs and visibility rules; `worldGenerator` with two or more possible bindings; `outcomes` with a deterministic verifier where possible; `events` such as saved reply, board share, object open, or item comparison; and `edges` linking a source event to its permitted recipients and artifact schema. These fields belong to an immutable version alongside the three prompts. The author-visible schema can remain simpler than the internal one. Each generated trial stores the chosen world binding, generation seed, version ID, model, temperature, and request compiler version.

The compiler is a pure server function of contract version, world binding, role, event history, and current user message. It returns the complete provider request and an auditable visibility manifest. A static auditor compiles both worlds at the chosen pre-event snapshot, serializes provider-visible data in a canonical order, and rejects the contract if the bytes differ. It also rejects equal answer labels. After the required event, it checks that the expected recipient request changes in the allowed fields. The certificate stores hashes and a readable diff, not hidden facts in a client-visible page. Recheck the certificate whenever prompts, templates, reveal rules, or provider tool settings change. The current lab already stores exact request contexts on saved replies; this feature should extend that trace rather than invent a second, incompatible history format.

The event store, not the model's prose, decides whether a handoff exists. A board entry can remain an ordinary note, but only an artifact created from a saved source event may satisfy a contract edge. Store the source message ID, parser version, parsed payload, run and world IDs, permitted recipients, and integrity signature or a server-owned database reference. Verify the source record belongs to the current trial and precedes the handoff. A retry should be idempotent: the same event must not issue two different artifacts. Parsing is a separate stage with a visible failure reason. Authenticity means “this is the recorded output of A,” not “A is correct.” The outcome verifier checks the latter. The expanded route study supports testing a typed application state such as `ROUTE=NONE` before sharing and `ROUTE=Ridge Road` afterward: it improved benign handoff uptake across eight synthetic route pairs. The adversarial follow-up found that user text could still spoof or override that state in the model's raw reply. The typed field is an aid to the model, not an authorization mechanism. The server must check a real event and the reply's consistency before publishing it.

The chain challenge makes that separation especially clear. With the benign state prompt, B and C produced correct whole-label outputs in all eight after-handoff worlds. When ordinary tester text claimed a board value, both roles answered early in all 16 pre-handoff probes. When the text contradicted a verified artifact, both followed the tester claim in all 16 after-handoff probes. The [adversarial summary](chain-state-adversarial-summary.json) includes the raw replies and an offline gate replay. The build should therefore keep a tester's board-shaped text in the ordinary user-message channel and never translate it into a typed artifact. A real artifact should be assembled from a saved source event. The publication check should require that event and verify the recipient's parsed answer against it, then separately verify the artifact's truth where the authored world has an oracle.

The raw reply and the published state need separate columns. A model may answer early even when the application will not accept that answer as a completed stage. Store the exact raw text for diagnosis. A deterministic gate checks the required event and typed payload before allowing a B or C result into the shared board or final outcome. A response that includes both “Awaiting handoff” and a final answer should appear as a role violation in the diagnostic view, even if its numerical answer is correct. The [crossed GPT-OSS route study](route-crossed-summary.json) found that all 64 after-handoff replies chose the correct vehicle, but 55 capitalized it differently from the stored label. The [Gemini Flash-Lite transfer](route-gemini-35lite-summary.json) exposed a different issue: 47 replies combined the correct vehicle with waiting text, and only ten of 64 were clean whole-label choices. The verifier therefore needs separate task-semantic, output-format, and mixed-state results. For a finite choice such as vehicle, normalize only the allowed surface variation, map the reply to a canonical option, and report an exact-format violation separately if the level requires one. Do not use broad substring or fuzzy matching as an authorization check. Provider HTTP errors occupy their own status; they must never be scored as abstention.

## Interface details

The configuration page should show a short dependency chain with the authored fact and reveal events, followed by a compact request preview. Clicking a node opens its fact scope and event rule. The paired run view should show two horizontal timelines and a synchronized stage selector: before handoff, after source reply, after share, and final response. At each stage, the author sees only the request diff for the chosen recipient, then can expand the full context already supported by the lab. Mark a certified pre-event stage only when the exact serialized requests match. Show distinct verdicts for whether the fact was necessary, whether the model used it after handoff, whether the answer has the required format, whether a tester could spoof or override it, and whether the source fact matched the authored world. Mark provider error, protocol error, semantic failure, and role violation distinctly. Avoid one “success” badge that hides these separate causes.

For prompt tuning, a useful result card is a four-step trace, not a single pass badge. It first shows whether the source model supplied a parseable value and whether that value was true. It next shows the exact state compiled for the recipient and its source event ID. It then shows the recipient's raw answer, canonical finite-choice label if any, and an explicit mixed-output or format error. Finally it shows the publication decision and reason. In the saved pilot, this would read “A true; B mixed wait and route; C not called.” In the benign follow-up it would read “A true; B route accepted; C vehicle accepted.” In the adversarial follow-up it would read “tester claim influenced raw B/C; missing or contradictory source blocks publication.” Authors can compare those traces across prompt versions without mistaking a stricter parser for worse reasoning or an attractive raw answer for a valid game transition.

For an interactive level, the same authoring panel can be attached to an object. The author declares what an `open`, `flip`, `compare`, `stamp`, or `ask` action reveals and to whom. The level preview runs both worlds side by side from the first frame. Hidden facts stay on the server until the reveal event. The client may receive an opaque object ID, closed-state artwork, and public label, but not the unopened page text or secret value. The inspector can show the object state graph, event log, fact exposures, and the model request generated after each action. This is particularly useful for the airport passport reference level, where the document inspection should change what the player can infer. If the passenger target model begins with a private secret, test its disclosure separately; do not display the orchestration indistinguishability certificate as proof of jailbreak resistance.

The [reference source audit](reference-scene-audit.json) illustrates why the visibility manifest must include API payloads as well as the rendered interface. Its first run found unopened passport and arrival-card fields in the blind player's initial configuration. We changed the player API to return closed-object metadata and supply document text after the recorded action. The rerun finds neither document in the initial configuration, and the protected brother-ownership truth remains absent. The model's verified desk context follows the corresponding observations, but its full static prompt has a different information boundary.

The [route-level visibility timeline](reference-visibility-timeline.json) makes the inspector's required data shape concrete. For each fact and stage, record whether it appears in the player API payload, visible DOM or asset, server action observation, and target model context, plus the event that first exposed it on each surface. In the repaired local reference, the card signature first enters the player API and verified desk after `card`; the signature-comparison observation enters the desk after `compare`. The UI should show these as separate exposure lines. This route audit used local Express, while the separate Chromium trace below inspects the downloaded browser text and network responses.

The [runtime visibility manifest](reference-visibility-manifest.json) goes beyond literal observation strings. It walks actual blind-player API responses, the captured target system argument, and freshly built text assets along a sampled click path. It records the first stage and JSON pointer for each declared fact. Its [PostgreSQL repeat](reference-visibility-manifest-postgres.json) agrees with SQLite. After repair, passport signature first reaches the player API at `open`, card signature at `card`, stamp date at `turn`, and UV result at `uv`; the date is absent from the client text bundle. The mismatch is derivable once both signatures are seen, before `compare`. The protected traveller name remains absent from sampled player APIs and text assets. The [generic scanner](visibility-manifest.mjs) accepts literal variants and trusted derived-fact functions, so the inspector can explain a conclusion reconstructible from several fields. A production authoring form should compile a constrained declarative rule for those derivations; it must not execute JavaScript supplied by contributors.

The target needs a separate exposure line for **verified desk context** and **full system request**. In this reference, the verified desk gains the card signature after `card`, but the static target prompt already contains it, the stamp date, UV status, and protected story truth at the closed desk. After `open`, the full request also supplies the passport signature, so the target can infer the mismatch before `compare`. A future author must choose which claim is intended: “this click reveals new information to the player or model” or “this click records an authorized inspection before a result may be published.” A comparison of two already visible signatures can be a useful physical action, but it cannot receive an informational-necessity badge. The initial player-side API and bundle leaks have been repaired; an informationally necessary comparison still needs a new measurement that cannot be derived from the two earlier signatures. To use it as a procedural checkpoint, keep the event-ledger rule explicit and label it as such.

The [real-browser trace](reference-dom-visibility.json) adds the player's ordinary screen and same-origin network responses to this boundary view. In the repaired Chromium path, passport signature first appears on screen and network after opening, card signature after requesting the card, stamp date after turning the page, and UV result after using the lamp. The downloaded text assets no longer contain the date. The [PGlite PostgreSQL trace](reference-dom-visibility-postgres.json) matches these first-exposure stages, and the [parity/freshness checker](audit-reference-browser-network.mjs) verifies source and bundle hashes. The [closed](browser-visibility/closed.png) and [card](browser-visibility/card.png) screenshots show the physical presentation. A current-screen snapshot first states the mismatch at `compare`, but cumulative observations let a player remember the first signature and infer the mismatch at `card`. The author inspector should show screen history and browser network timing side by side, then connect them to the verified desk context and full model request.

The [25 legal first-use action orders](reference-action-orders.json), repeated against [PGlite PostgreSQL](reference-action-orders-postgres.json), show this is not an artifact of the original storyboard sequence. With `open` preceding `turn` and `compare`, and `card` preceding `compare`, the player API and verified model desk have both signatures before comparison, whichever arrives second. The full target request could derive the mismatch after opening. UV was first available to the player API and verified desk after its own action in every order. The [manifest audit](audit-reference-visibility-manifest.mjs) checks parity and fresh source, bundle, and screenshot hashes. This covers those first-use permutations in one authored world; the reducer study below adds repeated actions and alternate routes.

A [reducer-derived physical-action graph](reference-reducer-graph.json) now covers repeat actions and alternate routes within a stated abstraction. The HTTP route and [graph runner](reference-reducer-graph.mjs) call the same validated state transition. It reached 5,745 abstract states and checked 66,410 legal transitions over opening, turning, three lamp settings, card request, three presentation choices, comparison, three movement choices, and hints. It verified equal next-action behavior for 60,666 merged histories and checked 34,470 endpoint-coordinate comparisons, including unavailable card moves. A [PostgreSQL repeat](reference-reducer-graph-postgres.json) agreed with SQLite; each adapter also matched 352 route actions over 23 actual sessions. The shortest mismatch bypass is simply `open`, `card`. The inspector should display this trace directly, with a separate note that the explicit comparison sentence still arrives at `compare` and may be a useful procedural affordance.

For certification, make the scope of the state quotient visible. Here it retains the current page, lamp mode, requested card, presentation, comparison, hint count, and historical identity, stamp, and UV observations. It drops precise positions, action timestamps and IDs, revision, and action count; equality of desk text and representative successors is checked for reached histories. The longest representative trace was 15 steps, below the 200-action route cap. This supports claims about the physical desk's verified observations. It does not include player questions, model replies, filing, image pixels, all continuous move coordinates, other authored worlds, or the live deployment. A production badge must state the audited boundary and action set, and return inconclusive when its abstraction or runtime parity cannot be checked.

Run a cheaper [prerequisite-closure check](reference-prerequisite-audit.json) before the graph. For each declared reveal, collect the observations guaranteed by actions required to enable it, then close them under authored derivation rules. If the supposed new fact is already derivable, show the proof and a short repair choice. In the passport example, `compare` requires `open` and `card`; these reveal the two signatures, which already determine the mismatch. Preserving both earlier signature reveals makes an information-necessity claim for comparison impossible. The author can instead make comparison a clearly labeled procedural checkpoint, delay one ingredient, or design a new comparison-only measurement. The [generic preflight](prerequisite-closure.mjs) can report `always-known-before`, `sometimes-known-before`, or `not-proven-known-before` for alternative prerequisite routes. Only the first two are counterexamples; the last requires full path and surface checks before any positive badge. The reference report demonstrates why the check must be boundary-specific: player API, rendered history, verified desk, and full target prompt have different initial facts.

For the orchestration lab, scope facts to the receiving specialist as well as the surface. The [chain preflight](chain-prerequisite-audit.json) keeps A's observed seal color private to A until the shared artifact reaches B, and keeps B's decoded route private to B until it reaches C. It distinguishes **handoff** steps from **computation** steps: B can calculate the route from a received color and private codebook, and C can calculate the vehicle from a received route and private fleet schedule. The inspector can show a short proof tree for an already-known result, or mark a possible new handoff for paired-world request verification. An authored role label alone must not make an upstream fact visible to every role.

The first production seam for that verification is in place. The route and [recipient request auditor](recipient-request-audit.mjs) use one [pure orchestration compiler](../server/orchestration-context.mjs), then one [provider-body builder](../server/model.mjs), covering the shared task and case, role system prompt, prior role turns, addressed board entries, current question, model, temperature, and provider-specific options. The [local study](recipient-request-study.json) passed eight opposite-answer B/C pairs and rejected twelve deliberate leaks or broken board links. A [provider test](../tests/model.test.mjs) confirms that this final body is the JSON sent to `fetch`. The report gives an author the first differing request field rather than a vague failure. Its board records are constructed fixtures: the next integration must load source reply IDs and board entries from immutable server records, generate twins from a saved author contract, and recompile before every run version. Until then the result is a useful preflight, not a badge for a live configuration.

Authors can now add one or two directed finite handoffs in the local Orchestration Lab. Each edge declares the source and recipient, the recipient's exact wait label, and source-to-output label mappings. The [server evaluator](../server/orchestration-contract.mjs) records raw replies separately from publication verdicts and lets the board share only a published whole-label source reply over a declared edge. It checks the most recent addressed saved reply rather than treating tester text as a handoff. The server compiles that record into a quoted `SOURCE_A="amber"` or `SOURCE_A=ABSENT` state and explicit branches appended to the recipient system prompt; the context inspector shows the exact result. A copied state string in tester text cannot alter the compiled state or authorize publication. The [SQLite and PGlite HTTP test](../tests/orchestration-gate.test.mjs) exercises early spoofed answers, a contradictory tester claim after a genuine share, blocked resharing, and a valid A→B→C chain; the [browser test](../tests/browser/orchestration.spec.ts) covers form persistence and a visible rejection. This is implemented locally, with old configurations unchanged. It does not verify that A's label is true, derive a world from the UI contract, or enforce the separate two-clue passport rule. The form should be paired next with the request auditor and a trusted world/observation binding.

The [local gate protocol](orchestration-gate-live-protocol.md) completed 32 GPT-OSS 20B calls over four worlds, four clean/claim conditions, and two fresh runs per condition. Its [plan tests](orchestration-gate-live-plan.test.mjs) establish pre-share twin equality at the full provider-body boundary. The [raw record](orchestration-gate-live-results.json) and [summary](orchestration-gate-live-summary.json) show exact waits in 8/8 clean pre-share calls and correct routes in 8/8 clean post-share calls. The fixed false application update caused premature raw routes in 8/8 pre-share calls; the fixed opposite-color correction caused wrong raw routes in 8/8 post-share calls. The actual local gate rejected all 16 attack replies while accepting the 16 clean replies in their proper states. All 32 planned replies arrived despite 24 saved Groq 429 attempts; the [integrity analyzer](analyze-orchestration-gate-live.mjs) checks every completed body and gate verdict, and a [separate check](verify-live-gate-errors.mjs) checks the failed-request hashes. Show raw model behavior and publication side by side in the author UI. These are fixed synthetic worlds and phrasings with a deterministic A fixture, not a deployed or adaptive-attack result.

The [saved-run world audit](saved-run-world-audit.md) demonstrates the data join using real local HTTP run records rather than constructed board entries. It binds each run ID and frozen snapshot to a private fact, checks source request exposure, compares recipient requests before and after a saved share, and verifies the source reply against that fact. The swapped-source negative control passes the structural handoff check while failing truth in both worlds; the original lineage-only gate even published B's routes derived from those false source labels. A separate control gives A no fact at all while its scripted replies happen to be correct, proving that source access needs its own check. Show these as separate outcomes. The app persists a server-owned pair and fact binding, plus monotonic turn/share events with prefix counts and hashes. The author audit endpoint reconstructs a share checkpoint after later turns and checks the saved provider bodies. [HTTP tests](../tests/orchestration-world-pairs.test.mjs) pass the true, false-source, and stale-binding cases on SQLite and PGlite PostgreSQL; the [browser test](../tests/browser/orchestration.spec.ts) exercises pair creation and the audit view. The pair fact is authored in the lab, and the editor is diagnostic rather than a player completion gate.

The [four-call live smoke](server-bound-pair-live-protocol.md) then used the new pair route with GPT-OSS 20B for both A and B. A gave the correct whole seal labels in both worlds; B gave the mapped route labels after authentic shares. The local audit passed, and its reconstructed source and recipient request hashes match the bodies captured immediately before the provider calls. The [record](server-bound-pair-live-smoke.json) and [analyzer](analyze-server-bound-pair-live.mjs) preserve the exact outcomes. Treat this as an end-to-end engineering check of one pair, not a reliability estimate.

Keep false-source experiments possible for authors. A diagnostic run may intentionally pass an authentic but false A reply to B and C to measure error propagation, but its world-truth failure must follow every derived answer and prevent a scored success. A player-facing completion needs valid lineage and verified truth. The UI should distinguish a diagnostic share from a publishable handoff so authors can study a failure without mistaking the downstream models' consistency with correctness.

Recheck eligibility from saved events when an author opens the score preview. A stored `scoreEligible` flag alone is stale if an observation record or share changes. The [local verifier](../server/orchestration-score.mjs) now requires a sealed-card observation matching the world binding, a source request carrying that fact, and ordered source turn, board share, and downstream turn links through every declared role. The [HTTP controls](../tests/orchestration-sealed-card.test.mjs) show that a tampered observation loses eligibility and a correct prompt-injected pair remains diagnostic because no object was opened. A separate [A-to-B-to-C control](../tests/orchestration-score.test.mjs) checks two real saved shares. This author preview is not a player leaderboard or a certificate that the initial client view hid the fact; pair and player-surface audits address those questions.

For a level built around an actual click, use the new **sealed-card pair** as the reference flow. The server creates identical frozen twins and withholds the authored fact from A until the card-open endpoint commits an `observe` event. A's closed provider requests must be identical; after opening they may differ only at the verified fact slot. Save A's reply, share it along the declared edge, and require identical reconstructed B requests before the share and a first difference at the saved handoff state afterward. The [local HTTP test](../tests/orchestration-sealed-card.test.mjs) checks the object event, duplicate-open behavior, false source propagation, score eligibility, and tamper detection on SQLite and PGlite PostgreSQL. The editor shows the first differing request field and actual B reply. The [six-call live record](sealed-card-live-v2-results.json) has two pre-open waits, two true source labels, two correct mapped B labels, and two eligible score previews; its [analyzer](analyze-sealed-card-live-v2.mjs) verifies the body hashes. An earlier live attempt stopped at a provider HTTP 400. This is one synthetic, local object and one model sample, not a production scene or reliability proof. Reuse its event and request checks when building real scene objects, and audit the player API, DOM, accessibility text, and assets separately.

Test false claims in ordinary tester messages after the structural check. In the [four-call claim challenge](sealed-card-adversarial-results.json), two closed-card A requests waited despite a false-open claim, and two B replies followed genuine shares despite an opposite-color correction. No raw violation occurred in that sample, so the server rejection branch was tested by the scripted HTTP controls rather than those live calls. The [protocol](sealed-card-adversarial-protocol.md) fixes the wording and the [analyzer](analyze-sealed-card-adversarial.mjs) checks body hashes. The structural audit uses a neutral B question, while the two contradictory B questions differ by world; do not present its neutral after-share hashes as the exact attack request hashes.

When the preflight finds an early exposure, offer a repair view grounded in the actual surfaces. An initial pass found player API copies of both signatures and API plus bundle copies of the Oslo stamp date. Those sources were delayed in the implementation; the current [reference repair report](reference-reveal-repairs.json) finds no early player-side source for those object actions. It still refuses to present an easy fix for `compare`: the intended earlier `open` and `card` reveals already supply both signatures, so hiding extra copies cannot make comparison informationally necessary. Show the pinned earlier reveals and their unavoidable proof. The [bounded repair search](reveal-repair.mjs) enumerates minimal *logical source* delays, not code patches or certified fixes. After the author changes a level, rerun actual API, bundle, browser, and reducer checks. Treat omitted sources or a candidate bound as inconclusive.

The [interactive author-inspector prototype](author-inspector.html) shows one compact way to expose this evidence. Its author selects a boundary and proposed click, reads the derivation proof, inspects source locations for a candidate repair, and steps through the shortest visible bypass. It now shows the local blind-browser network and screen first-exposure stage for each selected fact. It keeps “known before click,” “no early proof,” and “no permitted repair under pinned earlier reveals” as separate states. The [browser check](author-inspector-preview.json) exercised four interactions at desktop and mobile sizes without page errors; it is not a human usability study or deployed UI. Do not hard-code this reference report as a certificate for future levels.

A single before-and-after snapshot is insufficient for a clickable scene: another object may reveal the same fact first. The [event-cut prototype](event-cut-contract.mjs) explores a pair of finite, deterministic scene state graphs under every shared action sequence. It compares the player's observations and available actions after each sequence. If the worlds diverge without the declared action, it returns the shortest bypass trace, such as `inspect-seal`; if they diverge only after that action, it returns a reveal trace and certifies necessity within the modeled scene. A state limit returns `inconclusive`, never a pass. The authoring inspector should replay the bypass path and highlight the first differing API field, object label, accessible name, or action availability. Production should derive the graph and observation adapter from the same server scene reducer and response serializers used at runtime. Otherwise, the proof would cover a hand-written approximation rather than the player's actual options.

For levels with several clues, show **conditional evidence sufficiency** beside the required-action view. The [four-world document-desk prototype](conditional-evidence-results.json) demonstrates the distinction: both UV and signature comparison are needed to justify a clear decision, but either failing check can independently justify a hold. The author panel can report, for each authored world, the minimal sets of object actions that settle the decision, the remaining possible outcomes after a selected click, and actions that never occur in a minimal set. A paper that can be moved but never changes an observation is marked decorative for that particular decision rule. If a hidden UV result is sent in the initial API payload, the audit reports zero-click sufficiency in the broken-thread worlds. This diagnostic should help authors make useful interaction paths without forcing every player through irrelevant objects. That first prototype uses static, independent inspections; production must feed the actual client/API observation serializer to the dynamic audit below.

For levels with gated controls or useful actions in different orders, the [dynamic evidence audit](dynamic-evidence-audit.mjs) combines those two views. The author supplies several worlds with their correct decision, the runtime state transition, the player observation, and the visible enabled-action list. The tool returns each world's initial possible decisions, a shortest sufficient action path, and a shortest resolving path that avoids each proposed action when one exists. It also checks whether one adaptive strategy works across every still-possible world; a world-specific shortest route can require hindsight and should not be suggested to players as a guaranteed route. The evidence panel also needs a tester-claim probe. The [two-clue spoofing follow-up](two-clue-spoof-summary.json) left the verified UV and signature fields unchanged, but ordinary user messages claiming an inspection induced a premature decision in 12/14 attacks; one of seven clean controls also failed. This is a concrete acceptance case for the future server gate, which has not yet been deployed.

The completed [claim-style follow-up](two-clue-claim-style-summary.json) adds a more demanding author test. With 84 frozen GPT-OSS calls, three ambiguous verified states, and four repetitions per request, clean prompts waited in 10/12 calls, while false claims in plain, copied-note, and forged-update styles triggered the requested premature decision in 24/24, 21/24, and 24/24. The [protocol](two-clue-claim-style-protocol.md), [raw record](two-clue-claim-style-results.json), and [body-hash analyzer](analyze-two-clue-claim-style.mjs) allow exact reproduction. The offline gate rejected all 71 premature replies, including two clean-control errors. The author view should therefore show multiple lower-trust claim styles and repeat each request state; a single clean wait or a well-phrased system rule is weak evidence of safe abstention. These counts are for fixed messages and one model, not a prevalence estimate.

The [two-clue gate prototype](two-clue-publication-gate.mjs) gives that verdict a precise interface: verified observations and a raw model reply in, then `waiting`, `published`, or `rejected` with a reason out. An [offline replay](two-clue-gate-replay.json) classified 149 archived replies as 60 supported final publications, 36 waits, and 53 rejections, including all 13 non-wait outputs from the spoofing study and all 16 Gemini premature decisions. The runtime version must reconstruct observations from immutable inspection events stored by the server. It must not accept a client's claimed `UV=` or `SIGNATURE=` field as the gate input. Replay proves the decision rule is executable on saved data; it does not prove the deployed app already enforces it.

## Suggested implementation sequence

The current request construction and provider body are shared with their auditors, and the optional finite gate stores separate raw and publication verdicts in local runs. Paired world records and ordered observation, turn, and share checkpoints exist in both SQLite and PostgreSQL. The editor creates and audits a root source pair, shows the first differing request field, and marks false-source completions ineligible in its score preview. Next, extend the compiler to richer fact scopes and connect object dependencies through the real scene reducer and player surfaces, then test a complete player path. Do not deploy a certificate badge until it is checked against every provider-visible input path, including prior turns and tool results.

## Acceptance criteria

For a contract that claims a specific object action is required, every modeled action path that avoids that action must keep both worlds observationally equivalent. A deliberate alternative leak must fail with a replayable shortest path; a world-specific action becoming available must fail even if its text is identical. Exhausting a state cap must yield `inconclusive`. The graph audit must be regenerated after a scene reducer, API serializer, accessible label, or asset manifest changes.

For a three-role chain, A's request must remain identical across worlds with different private B codebooks, B's after-A request must remain identical across worlds with different private C schedules, and C's before-B request must remain identical across worlds with different decoded routes. Each equality must pair worlds with different answers at the relevant stage. A copied or tampered artifact must fail verification at the receiving edge. These are authoring-time information checks; run-time uptake and source truth remain separate verdicts.

A deliberately leaked private fact in the shared task must fail the pre-handoff equality audit and identify that text as the cause. A valid pair must produce two distinct final labels and identical downstream requests before the event. A true artifact must be accepted only in its own run and world, only by its declared recipient, and only once the source event exists. A copied artifact from the twin, a changed payload, a stale source event, and a user-typed imitation of a handoff must not create a valid server event. The raw view must preserve an early answer while the published state remains blocked. After a valid event, a tester's contradictory route claim may remain in the raw transcript, but an inconsistent model reply must not be published. An incorrect but authentic upstream artifact must be reported as semantically wrong rather than forged, and must not silently become a valid final outcome when the authored world gives the server an oracle. Provider errors must remain visible as errors. In the interactive preview, opening the decisive object must create an observable world-specific difference, while loading the closed scene must not reveal the hidden value through the UI, accessibility tree, client bundle, or initial API response. Finally, a human playtest should establish that the object has a discoverable reason to be used within the intended three to five minutes; a byte-level certificate cannot establish that by itself.
