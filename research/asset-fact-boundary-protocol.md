# Observer-relative asset fact study

Frozen before capture on 3 October 2026. Use the same local blind passport preview, client build, URL, port, and 1440 by 1000 Chromium viewport for four isolated fixtures. Hold the UV thread intact. Cross the card-signature value (`E. Vale`, `N. Vale`) with two asset carriers at the initial passport-cover URL: visible raster lettering and WebP EXIF `ImageDescription`. Generate the two images within each carrier from one template, changing only the signature value. The cover is available before the arrival card is requested.

For each fixture, collect the intro player API, body text, accessibility snapshot, every same-origin GET path/status/body hash, the downloaded cover's raw decoded pixels and metadata, and a full-page screenshot's raw decoded pixels. The visible-raster pair should have identical API, DOM text, accessibility, and resource paths; the cover bytes, cover pixels, and screenshot pixels should differ. The metadata pair should also have identical API, DOM text, accessibility, and resource paths; cover bytes and declared EXIF should differ, while cover pixels and screenshot pixels remain identical. All other GET body hashes must match within each pair. Record the first differing resource path as a witness.

This is a deliberately injected counterexample, not a claim about the ordinary art. The visible lettering is reviewed from screenshots; it is not identified by an OCR model. Metadata is available to a player who downloads or inspects the asset, not to a player who only looks at the page. Pixel equality cannot certify source-byte equality, and source-byte equality across worlds is sufficient only for this asset at the captured state. Resource presence, status, and content type also count as observations even when response bodies match. The test does not cover request timing or cross-resource load order, later image swaps, caches, browser extensions, visual recognition error, or target-model behavior.
