# Counterfactual Handoff Contracts: Testing Whether an Interaction Is Necessary

**Research draft, 3 October 2026.** This is a proposed authoring and evaluation method with controlled engineering pilots, not a validated benchmark or a claim of priority over all related work. The associated [prototype](handoff-contract.mjs), [tests](handoff-contract.test.mjs), and [raw pilot record](paired-world-pilot.json) are in this directory.

## Abstract

An orchestration game can appear to require several specialists while one model can infer the answer from their shared case. An interactive level can display clickable documents while a decisive fact is already in an API response or image. We propose a **counterfactual handoff contract**: authors declare a fact and reveal event, then generate worlds with different correct outcomes but identical recipient input before that event. A finite-state action audit searches for bypasses; an observer-relative browser audit compares API data, accessible text, rendered pixels, and downloaded assets along selected action histories. In the passport reference, the signature mismatch is knowable before `compare`. A deliberately altered open-book asset exposes the card signature at `open`; omitting that asset from the state graph produces a false `card` certificate, while a browser replay catches the leak. These are information-level findings within declared observation boundaries, not guarantees about what a player or model notices. Controlled model studies separately test uptake, response format, forged claims, source truth, and publication. In an 84-call two-clue follow-up, fixed false claims elicited 69 requested premature decisions in 72 attack calls; an offline observation-keyed gate rejected them. In a separate 32-call local HTTP study, B gave all 16 clean required replies but followed a fixed false tester claim in all 16 attack calls; the actual server gate rejected those violations. A 36-call transfer using browser-recorded equipment observations produced 36 evidence-consistent whole-label replies, including 12 fixed false-claim calls, but a punctuation-sensitive exact gate rejected 17 harmless wait variants. The result is an authoring workflow with distinct verdicts for informational necessity, source access, source truth, model behavior, response grammar, and publication. The studies do not estimate general reliability or establish priority over existing counterfactual, provenance, or visual evaluation methods.

## The design problem

The current Orchestration Lab has three editable system prompts, one shared task and test case, independent conversations, a common board, and frozen run history. Its server sends the same test case to every slot. This supports prompt experiments, but a later specialist can sometimes infer the final answer without reading the board. The common board makes a reply available, yet an identical answer before and after sharing does not show whether the board caused anything. In an interactive scene, a clickable item can have the same problem: it is animated and attractive, but its information is already available elsewhere. These are failures of **causal level design**, even when the final answer is correct.

We want authors to be able to make a stronger statement: “This recipient needs this handoff to distinguish the two possible states of the case.” The proposed contract turns that statement into a falsifiable property of the actual requests assembled by the server. The author chooses a hidden variable, two values that change the correct outcome, the actor allowed to observe it, the action that transfers it, and the later actor expected to use it. The compiler produces paired worlds and checks each request at the point where it crosses the model or player boundary.

## Position relative to existing work

Multi-agent role play and conversation frameworks such as [CAMEL](https://arxiv.org/abs/2303.17760) and [AutoGen](https://arxiv.org/abs/2308.08155) show how to organize specialist exchanges. [MultiAgentBench](https://arxiv.org/abs/2503.01935), [InformativeBench](https://arxiv.org/abs/2406.14928), and [AgentWorld](https://arxiv.org/abs/2609.31590) evaluate collaboration and information asymmetry at broader scales. AgentWorld's Causal Collaboration Effectiveness traces which observed actions contributed to a result. Our question is narrower and earlier in the design process: before any run, can an author establish that the intended recipient has no distinguishing input until a particular handoff? This is a proposed distinction in purpose and method, not evidence that existing systems could never support such a check.

There is also close work on controlled interventions. [CAGE-CAL](https://arxiv.org/abs/2605.30653) compares communication with a matched no-communication graph to calibrate agreement. [When Upstream Messages Override Correct Answers](https://arxiv.org/abs/2609.36855) holds downstream evidence fixed and changes the upstream message, showing why the truth of a handoff cannot be assumed. [AgentAbstain](https://arxiv.org/abs/2607.10059) generates near-identical act-or-abstain task pairs. Our pairs have a different invariant: the receiving actor's complete pre-handoff input is **identical** across worlds whose correct outputs differ. The invariant is useful for authoring an information dependency. It does not replace those studies' measurements of abstention, collaboration, or message-induced error.

[Counterfactual Trace Auditing](https://arxiv.org/abs/2605.11946) pairs with-skill and without-skill agent traces, aligns their phases, and reports behavioral changes beyond pass rate. This is close to our proposed author-facing timeline comparison. Its intervention changes the presence of a skill on the same task; ours changes an authored hidden fact while holding the recipient's pre-event request fixed and requiring opposite correct outcomes. Paired traces and phase alignment are established methods, so neither is a novelty claim here.

Further counterfactual evaluation makes a broad novelty claim inappropriate. [AgentBoundary](https://arxiv.org/abs/2609.33658) varies apparent risk and permission in executable workflows to separate safety from task competence. [Spurious Tool Use](https://arxiv.org/abs/2609.16268) tests whether agents invoke tools for causal task reasons rather than surface cues. [GroundEval](https://arxiv.org/abs/2606.22737) checks whether an agent's answer followed a permitted, time-valid evidence path, and [AttriGuard](https://arxiv.org/abs/2603.10749) uses runtime counterfactual re-execution to attribute proposed tool calls. Our current evidence supports a more specific application-level contribution: before authors publish a level, check from its actual request and scene builders whether their chosen handoff or object action can be the first source of a decisive fact; when it cannot, show the earliest leak and a scoped repair or impossibility proof. We have not shown that this exact workflow is absent from all prior systems, nor that the method improves human-authored levels in a controlled study.

[ToolChoiceConfusion](https://arxiv.org/abs/2606.06284) also uses precondition-effect contracts to expose a causally sufficient next-step tool frontier. It optimizes what tools an agent sees during task execution; our conditional-evidence analysis asks a level author which object actions can settle a designed decision and whether one declared action is bypassable at player and model boundaries. This nearby causal-sufficiency framing further limits any claim that action pruning or minimal evidence sets originated here.

Runtime information-flow methods already address important parts of this space. [CaMeL](https://arxiv.org/abs/2503.18813) separates control from untrusted data, and [Fides](https://arxiv.org/abs/2505.23643) applies information-flow control to agent systems. The contract proposed here is primarily a **design-time generator and auditor** for a required gameplay or orchestration dependency. Signed artifacts and server-side gates are implementation choices, not a novel general solution to information-flow security. [AgentDojo](https://arxiv.org/abs/2406.13352) further shows the value of dynamic attacks against an agent rather than relying on one fixed prompt. Our evaluation plan therefore includes forged, stale, and swapped handoffs.

[ARGUS](https://arxiv.org/abs/2605.03378) is particularly close to the runtime side of our proposal: it audits whether a proposed agent action has a benign, provenance-grounded justification before release. [Authenticated prompts and context](https://arxiv.org/abs/2602.10481) likewise address the integrity of workflow inputs with cryptographic lineage. These make a broad claim to have invented provenance-based action authorization untenable. Our narrower design question is whether an author-declared *interaction* is informationally necessary in the first place, including whether an unopened browser object already reveals its answer in a client payload, and which optional actions suffice under each world. The live spoofing runs motivate pairing that authoring audit with an established kind of runtime evidence gate; they do not prove a new security primitive.

[AgentSecBench](https://arxiv.org/abs/2605.26269) explicitly separates a prompt's description of a security boundary from enforcing observation projections, capability limits, and output validation; it also uses paired adversarial and benign controls. [Beyond Single-Model Injection](https://arxiv.org/abs/2609.22949) studies inter-agent message injection and reports defenses based on message provenance and scoped access. These are especially relevant to our saved-board gate. They reinforce that our paired controls, provenance tracking, and output validation are applications of established ideas. The remaining authoring claim must be tested at the level of a particular declared handoff or object action and its actual request and client surfaces.

[Evidence-Carrying Multimodal Agents](https://arxiv.org/abs/2605.19192) is close to the source-truth gap in our prototype: it grounds action-critical predicates in constrained DOM, OCR, or accessibility verifiers before a deterministic gate authorizes a tool action. Our saved handoff gate checks that A's label came from a published reply. The sealed-card mode now compares that label with a server-owned fact, records its open event, and recalculates author score eligibility from the event and handoff chain. It does not verify a physical player's visual observation through DOM, OCR, or accessibility evidence. A future player score gate would connect those surfaces to an immutable level world, rather than introduce a new general authorization principle.

Explicit state specifications and compiled workflow control are also established directions. [FASTRIC](https://arxiv.org/abs/2512.18940) makes implicit finite-state behavior explicit in natural-language prompts and measures procedural conformance across models and formality levels. [COVENANT](https://arxiv.org/abs/2607.25400) compiles natural-language workflow instructions into a control-flow graph whose runtime interpreter checks proposed steps before committing state. Our B ablations are consistent with the practical value of explicit branches in one sampled task, but they do not establish that branch-table prompting is new or generally optimal. The proposed contract adds a different authoring question: before a declared handoff or object action, are opposite correct outcomes indistinguishable to the actor at the actual request boundary? The intended sandbox combines that necessity check with prompt conformance and a runtime publication decision; neither prompt formality nor a gate alone certifies necessity.

The [execution-provenance survey](https://arxiv.org/abs/2606.04990) makes clear that typed evidence lineage and process-level accountability are broader research areas, so our artifact record should be treated as an application of that work. [WebMCP-Phalanx](https://arxiv.org/abs/2608.24017) also separates tool provenance from semantic prompt inspection and identifies a call-timing gate under adaptive attack. This reinforces our narrower engineering rule: the sandbox's server checks a saved event before it gives any downstream role a privileged artifact; a persuasive sentence cannot create that event.

Recent work narrows the claim further. [When “Must” Becomes “Maybe”](https://arxiv.org/abs/2608.24569) tests whether binding constraints survive handoff transformations. [Facts Without Rules](https://arxiv.org/abs/2608.29028) examines loss of boundary metadata in summaries, and [Beyond Final Accuracy](https://arxiv.org/abs/2610.01042) separates helpful correction from harmful answer changes during communication. Our proposed contribution is the authoring-time certificate for a *declared interaction* and the combined necessity, uptake, and authorization audit in an interactive sandbox. Structured state and output gating themselves are not claimed as new inventions.

The game-theoretic foundation is older than LLM sandboxes. [Games in Dynamic-Epistemic Logic](https://onlinelibrary.wiley.com/doi/abs/10.1111/1467-8586.00133) treats local actions as changes to players' information, and [verification of imperfect-information systems with public actions](https://doi.org/10.65109/EKDQ8015) studies knowledge over action histories. Our reducer-derived graph is an engineering application of that tradition, not a new epistemic logic or a general model checker. Its practical target is a level author who needs a shortest bypass trace across the actual HTTP, rendered, and model-request surfaces.

Graph path selection and edge coverage are established model-based testing techniques. [Optimal path-based test selection](https://doi.org/10.1016/j.infsof.2019.06.006) studies set-cover-based selection under edge and edge-pair criteria, a [web-application experience report](https://arxiv.org/abs/2104.02152) describes practical model-based end-to-end testing, and [grey-box GUI sequence generation](https://arxiv.org/abs/1205.4928) uses event dependencies to reduce the tested action space. Our eight-path equipment cover is therefore a cost calculation, not an algorithmic novelty claim. The research question is whether reducer-selected paths preserve an *event-relative paired-world information boundary* in the browser's actual API, accessible text, pixels, and downloaded bytes. Edge coverage makes that experiment cheaper; it does not prove all-path browser noninterference. The order-sensitive mutation below makes that limitation concrete.

[Orchestrated Reality](https://arxiv.org/abs/2606.16014) also models a playable LLM world as canonical state, parameterized actions, an observation projection, and validated state changes. That architecture is close to the scene substrate we need. Our current sealed-card object is much smaller: a server-owned fact and one open event. The research question here concerns an author-declared dependency across different observers and actual delivery surfaces, followed by a score that can be traced through the recorded interaction. We should not present canonical world state or content-hashed transitions as new techniques.

The attack side also has close prior art. [Prompt Injection as Role Confusion](https://arxiv.org/abs/2603.12277) studies how lower-trust text that imitates a privileged role can acquire apparent authority in a model's behavior. [NetInjectBench](https://arxiv.org/abs/2607.10490) evaluates prompt-level defenses and a metadata-aware action gate in a different domain. These results motivate testing several tester-claim styles and separating raw model behavior from server publication, but neither role-spoof probes nor metadata gates are claimed as inventions here. Our distinctive question remains whether the particular authored handoff or physical inspection is informationally necessary at each relevant application boundary.

Repairing a failed design property is also an established research direction. [Guided Game Level Repair](https://arxiv.org/abs/2410.23101) targets unsolvable generated levels with explainable, constraint-guided edits; [Repairing General Game Descriptions](https://arxiv.org/abs/2508.10438) studies minimal changes to faulty formal game rules; [Type-Driven Repair for Information Flow Security](https://people.csail.mit.edu/polikarn/publications/lifty.pdf) repairs program-level information-flow violations. Our bounded source-delay search does not invent minimal repair. It asks a narrower authoring question: which concrete early API, asset, or prompt exposures would have to move to make a *declared interaction* informationally necessary, while preserving facts that earlier object actions are supposed to reveal? A failure under those preservation constraints tells the author to change the information design, not merely hide another copy of a string.

## Contract and guarantee

Let $w_0$ and $w_1$ be two authored worlds. Their correct final answers $y_0$ and $y_1$ must differ. Let $I_r(w,t)$ be the complete request or observation delivered to recipient $r$ at time $t$, including system prompt, messages, visible object state, tool inventory, and any retrieved data within the chosen boundary. For a required event $e$, the contract requires

\[
y_0\ne y_1,\qquad I_r(w_0,t^-) = I_r(w_1,t^-),\qquad I_r(w_0,t^+)\ne I_r(w_1,t^+),
\]

where $t^-$ is immediately before the authorized event and $t^+$ is immediately after it. The prototype compares the compiled model-visible request context; a production compiler must compare the serialized request actually sent, including any tool results or provider features. A certificate should record the shared pre-event hash, differing post-event hashes and answer labels, the event that changed visibility, and the source artifact. For a level with several required objects, the author makes one pair per decisive dependency edge. A proposed dependency fails if another visible route leaks the differing fact before the intended event.

**Proposition.** Suppose $I_r(w_0,t^-)=I_r(w_1,t^-)$, the recipient has no world-correlated side channel or persistent memory, the worlds are sampled equally, and an exact answer can be correct for at most one of them. Any model policy has mean exact pre-handoff answer accuracy at most $1/2$ across the pair. For a deterministic policy it must give the same answer in both worlds and be wrong in at least one. For a stochastic policy, the output distribution is the same under both inputs, so

\[
\frac12\Pr(Y=y_0\mid I)+\frac12\Pr(Y=y_1\mid I)\le\frac12.
\]

This is an information claim, not a behavioral one. A model can still confidently guess, produce a plausible answer, or violate its role. The desired pre-handoff behavior is to wait or request the missing artifact. A separate deterministic output gate can prevent a premature final answer from being published, while a raw-response view lets authors see that the underlying model attempted it. The equality certificate is only as sound as the boundary being audited. It must include every string and tool result the recipient can access, and it does not protect against information leaked through client code, cross-run memory, timing, external search, or a player's prior knowledge.

Request equality also needs a **world-fidelity check** before it can be interpreted as a meaningful game experiment. For every declared fact slot, the compiler should verify that a visible value agrees with the authored world, while a hidden value is absent from that recipient's request. Otherwise two requests may be byte-identical because both copied the same default fact, even though that fact is false in one world. The information bound above still holds mathematically for a recipient given those bytes, but the pair no longer represents the intended cases. This is recipient-scoped: a source specialist may know the world-specific fact from the start, while a downstream specialist or player must not. The passport counterfactual check below finds exactly this failure at the target's static prompt while the player API and verified desk projections behave as authored.

### From a snapshot to an interaction path

For a clickable level, equality at one pre-event snapshot is too weak. A player may inspect a different object first or notice that an action is available in only one world. The stronger **event-cut certificate** treats the two scenes as finite, deterministic state machines. Let $H(w,\tau)$ contain the sequence of observations and available-action sets along action trace $\tau$. For every reachable trace omitting the declared action $e$, the certificate requires equal histories; at least one trace containing $e$ must distinguish the worlds:

\[
\forall\tau\in\mathcal T_{\neg e},\ H(w_0,\tau)=H(w_1,\tau),\qquad
\exists\tau\in\mathcal T_e,\ H(w_0,\tau)\ne H(w_1,\tau).
\]

Thus $e$ lies on every *modeled* distinguishing path, although the reveal may occur on a later action. A different available-action set is itself a distinguishing observation and fails the first condition. This applies the established idea of observational equivalence in interactive noninterference to an author-declared gameplay dependency; it is not a claim to have invented noninterference. See [Semantics for Interactive Sequential Systems and Non-Interference Properties](https://ejbeta.clei.org/cleiej/article/view/160).

The [finite-state prototype](event-cut-contract.mjs) explores paired states by breadth-first search and returns the shortest bypass path and first differing field when another action reveals the difference. It can also enumerate inclusion-minimal *sets* of actions covering every distinguishing path, which accommodates levels with more than one legitimate way to discover a clue. Its [tests](event-cut-contract.test.mjs) cover a required comparison, an alternate inspection, world-specific action availability, a delayed reveal, minimal action sets, and an exhausted state limit. The limit returns `inconclusive`, not a certificate. This is a precise answer to a practical authoring question: “Can a player learn the answer by clicking something else?” An [author guide](event-cut-author-guide.md) translates the audit into level-design steps. The claim only covers the declared state machine and observation adapter. To test a real web level, those observations must include API responses, accessible text, asset metadata, and model request context, and the graph should be derived from the runtime reducer rather than duplicated by hand. The passport reference initially failed a stricter object-dependency claim for exposed document fields; the player API was repaired as discussed below.

### Conditional evidence rather than mandatory clicks

A single required-action claim can also be too strong. Consider a fictional document desk that should clear a case only when a UV thread is intact **and** two signatures match. A broken thread alone settles `hold`; a mismatch alone also settles `hold`; a clear result requires both inspections. For an action history $h$, let $B(h)$ be the authored worlds compatible with everything the player has observed, including the initial API response. The currently possible decisions are $D(h)=\{y(w):w\in B(h)\}$. A decision is supported by the available evidence precisely when $|D(h)|=1$. An action set is *minimally sufficient* for a world if observing those actions makes its decision unique and no proper subset does. This is a finite, deterministic authoring diagnostic, not a claim that the model or player will reason correctly.

The [conditional-evidence prototype](conditional-evidence-contract.mjs) enumerates those sets across four authored worlds and three clickable actions. In the intact-thread, matching-signature world, both `uv` and `compare` are needed to justify `clear`. When only the signature mismatches, `compare` alone is sufficient for `hold`; when only the thread is broken, `uv` alone is sufficient. If both fail, either one alone suffices. Moving a paper never belongs to a minimal sufficient set, so it is physically interactive but informationally decorative in this specification. After observing an intact UV thread, the decision remains ambiguous and comparison is still useful; after observing a broken thread, further comparison cannot change the decision. The [study record](conditional-evidence-results.json) and [tests](conditional-evidence-contract.test.mjs) reproduce these claims. A negative control puts the unopened UV result in the initial API view: both broken-thread worlds then support a zero-click `hold`, exposing why client payloads belong in a reveal audit.

The static calculation treats tests as freely available and order-independent. We added a [dynamic belief-state audit](dynamic-evidence-audit.mjs) for authored scenes where opening a panel enables a measurement and the set of available controls is itself visible. At each step it retains only worlds consistent with the player's entire observation and action-availability history. It searches for the shortest trace that makes the *decision*, rather than the complete hidden world, unambiguous, and reruns that search with each action omitted. An action is necessary for one world only when no resolving trace for that world omits it. The tool separately computes a uniform adaptive policy: the player chooses from the actions currently visible, then can change course after seeing the result. This avoids presenting a hindsight-only shortest path as a guaranteed strategy. The study uses a separate four-world [equipment-inspection fixture](dynamic-evidence-fixture.mjs): release requires stable voltage and an intact fuse; either failure supports hold. In the [saved four-condition result](dynamic-evidence-study.json), the baseline has 24 belief states and 46 transition edges. Stable voltage with an intact fuse requires inspection, panel opening, and measurement; a blown fuse supports hold after one inspection; unstable voltage can support hold after opening the panel and measuring. With both failures, neither test is individually mandatory because either route settles hold. A clipboard move is ordinarily decorative. Inspecting the fuse first gives a guaranteed adaptive decision within three actions. An independently enumerated, unmerged set of action histories [agrees with the graph](dynamic-evidence-audit.test.mjs) on shortest resolution, action necessity, and worst-case adaptive depth for all four conditions. A three-world negative control gives every world a one-click resolving path but no first click that can resolve *all* worlds; the tool reports no guaranteed adaptive policy in that case.

We then put this *same equipment reducer* behind a local HTTP endpoint and a visual [inspection bay](equipment-browser-client.html), rather than writing a second set of browser facts. The [browser study](equipment-browser-study.json) compares voltage twins and fuse twins over four action paths, including moving the clipboard and opening the panel before the decisive inspection. Fourteen Chromium fixtures and 32 screenshot stages show equal opening DOM text, accessibility tree, pixels, and GET bytes for each clean pair. Across 20 baseline channel/path verdicts, DOM, accessibility, pixels, and POST action payload first differ at the declared inspection; GET-only bytes remain equal because the clue travels in a POST response. The server rejects a premature `measureVoltage` request in every fixture without changing state, and every successful response matches the reducer's observation and enabled-action list. Three injected controls are detected: a voltage value in the opening API, fuse-dependent button availability on load, and a clipboard shortcut that reveals voltage before the meter. The [protocol](equipment-browser-protocol.json) records one correction to the shortcut path after an initial partial run, and the [freshness audit](equipment-browser-audit.mjs) recomputes channel verdicts and checks source and screenshot hashes. [Opening](browser-equipment/baseline-stable-intact-openPanel-measureVoltage-intro.png) and [measured](browser-equipment/baseline-stable-intact-openPanel-measureVoltage-measureVoltage.png) screenshots were visually reviewed. This transfers the graph/browser check to a second scene family, but it is a research-only client, not a production level, and the tested paths do not exhaust every browser action history.

A locked [first-use follow-up](equipment-first-use-protocol.json) enumerated every legal complete order of the four equipment actions, rather than only the four selected paths. There are 12 orders per one-factor pair. The [Chromium report](equipment-first-use-study.json) contains 48 world/path fixtures, 240 screenshot stages, and 120 channel verdicts. In all 24 paired paths, DOM text, accessibility, pixels, and POST payload first diverged at the factor's declared inspection; GET-only bytes did not diverge. The [audit](equipment-first-use-audit.mjs) rechecks source hashes, legal paths, screenshot pixels, and all verdicts. An exploratory [exact transition-cover calculation](equipment-transition-cover.json) then asked how many of the 12 paths are needed to traverse every distinct reducer state/action edge. The answer is eight paths covering 20 edges for either pair; the smaller selected subset also has the expected browser verdicts because the full set was run. This offers a way to choose a defensible browser replay suite when path count grows, but edge coverage alone cannot certify untested browser histories or hidden asset and timing behavior. The first-use study omits repeated actions and target-model conversations.

We tested that limitation with a locked [order-sensitive mutation](equipment-order-mutation-protocol.md), [four-fixture Chromium run](equipment-order-mutation-study.json), and [independent recomputation audit](audit-equipment-order-mutation.mjs). The mutant client asks a debug endpoint for voltage only after `openPanel → inspectFuse → moveClipboard`, one legal prefix omitted by the eight-path edge cover. A selected path, `inspectFuse → openPanel → moveClipboard`, reaches the same reducer state before measurement. In the two opposite-voltage worlds, the omitted path exposed stable versus unstable in rendered text, accessibility, pixels, and GET bytes at `moveClipboard`; its ordinary POST action response still first differed at `measureVoltage`. The matched selected path first differed at `measureVoltage` on the four ordinary channels and never fetched world-specific GET bytes. All 20 screenshots, their decoded pixel hashes, ordinary POST bodies, source hashes, and ten channel verdicts were audited; the two premature screens were visually checked. This is a constructed browser-specific fault, but it demonstrates that a state/action edge cover can miss an implementation path dependency not represented in the reducer. For authoring, a compact path suite needs explicit order-sensitive fault controls or stronger dependency coverage, and a passing subset must retain its sampled-path scope.

Formally, a belief node $B$ contains the possible world and runtime-state pairs consistent with the observation history, including the displayed action list. Let $D(B)$ be its set of correct decisions and $A(B)$ its common displayed actions. For deterministic transitions, the worst-case number of further actions under the best adaptive strategy satisfies

\[
V(B)=\begin{cases}
0, & |D(B)|=1,\\
1+\displaystyle\min_{a\in A(B)}\max_{o\in\operatorname{Obs}(B,a)}V(U(B,a,o)), & \text{if a resolving policy exists},\\
\infty, & \text{otherwise}.
\end{cases}
\]

Here $U$ updates the candidate worlds after action $a$ and observed result $o$. The implementation solves this finite reachability recurrence by starting unresolved nodes at infinity and propagating finite values backward. It reports the per-world existential shortest path separately from $V(B)$, since the former may select an action using hidden knowledge of the true world. This is a deterministic worst-case count, not a prediction of how long a person will take or how an LLM will answer.

The controlled changes show why the UI and API belong in the information boundary. Putting voltage in the initial payload makes both unstable worlds zero-click decisions. Showing an Inspect fuse control only when the fuse is blown also makes both blown-fuse worlds zero-click decisions, even though no text states the fuse condition. Making the clipboard move expose voltage creates a one-click bypass of the intended measurement. These are deterministic authoring counterexamples, not estimates of model behavior or player success. The method inherits ideas from [dynamic epistemic games with precisely described actions](https://arxiv.org/abs/2001.07141) and [active test selection over hypotheses](https://arxiv.org/abs/2312.15357). Its sandbox contribution is a concrete decision-oriented audit over a level's compiled observation and action surfaces; it does not invent belief-state reasoning. The current fixture is separate from the production client and ignores timing, images, unmodeled network responses, stochastic observations, and human memory limits. Its finite-state bound returns inconclusive, so integration must derive transitions and visible controls from the actual level before a production claim is made.

We next connected that auditor to the [passport scene's production physical reducer](../server/passport-reference.mjs) through a [first-use action adapter](passport-dynamic-adapter.mjs). The reducer and document/verified-desk serializers now accept an internal scenario parameter; the shipped reference still uses its original facts. Four research-only variants cross matching versus mismatching signatures with intact versus broken UV thread. For this experiment alone, the hypothetical document decision is `clear` only when both checks pass, otherwise `hold`. That decision is **not** the game's jailbreak-success criterion, which depends on an actual target disclosure. The adapter admits first uses of open, turn, request card, UV, compare, and one passport move; it excludes repeated actions, hints, questions, filing, and other movement coordinates. Its player observation includes the same staged documents and action observations as the local API response, and its verified-desk view calls the same context builder used for target requests.

The [SQLite result](passport-dynamic-study.json) and [PGlite PostgreSQL repeat](passport-dynamic-study-postgres.json) each explore 1,525 belief states and 1,524 transition edges on both audited boundaries. The local HTTP parity check compares the actual default-world responses against reducer-derived documents and desk context at 14 stages and 12 actions per adapter, using two different action orders. The [freshness and parity checker](audit-passport-dynamic-study.mjs) also checks the existing real-browser trace: in the default world, the card and derived mismatch enter the sampled browser at `card`, and the UV result at `uv`. Across the four counterfactual variants, the decision can be reached within two actions by an adaptive strategy. A mismatching card alone settles hold; a broken UV thread alone settles hold; the passing world needs both. Compare is on no required resolving path because its result is already inferable from the card and passport signatures. This agrees with the earlier single-world comparison bypass, now under a different, explicitly declared document decision. The action adapter is source-derived. The variants are now separately routable in the local research fixture. The earlier browser trace covers only the shipped default world; a new four-world browser test checks rendered signature and UV changes after the corresponding clicks, but does not certify image pixels or every action order. A direct consistency check of the production target prompt finds contradictions in **three of the four** research variants: it still asserts the default card signature or intact UV thread. The unchanged public prompt is therefore a useful negative control, not the prompt used by the new local variant routes. Each study version now compiles its own card and UV facts from the typed world state. The complete target requests are world-consistent, but they differ across worlds before inspection because the target starts with private story and document facts. This supports a player-boundary reveal claim, not pre-action indistinguishability of the full target request.

The [routed-world study](passport-routed-worlds.json) and [PGlite repeat](passport-routed-worlds-postgres.json) start four distinct immutable local level versions through actual HTTP routes, perform open, card, and UV actions, capture each completion stub's complete input, and hash the exact body produced by the production provider-request builder. The [freshness and parity audit](audit-passport-routed-worlds.mjs) checks both adapters. The four initial player *API configurations* and closed document payloads are equal, while all four initial target prompts differ. After inspection, each player response and target request agrees with its world's card signature and UV result. The [browser test](../tests/browser/passport-research.spec.ts) visits all four author-diagnostic research routes, clicks the objects, checks the response and rendered note, reloads, and confirms the ordinary reference has no research session. Those routes visibly name the world in the URL and heading. They therefore cannot support an identical player-view claim, despite the equal API configurations. The generic chat, hint, submit, and branch endpoints now reject these desk versions, preventing a route that would omit the physical context. A browser-suite failure exposed a separate shared-IP throttle defect: successful developer entries were counted as failed sign-in attempts. The limiter now budgets failed and in-flight attempts, and a regression test covers 16 successful invitations followed by blocked repeated failures. The local fixture uses a deterministic completion stub, so this is a boundary and implementation check, not a live model compliance result or a human usability study.

We added a separate, research-only **blind player preview** that selects the world in an isolated server fixture while preserving the same `/reference/research/preview` URL, client bundle, and port. The [browser protocol and its amendment](passport-blind-visual-protocol.md), [Chromium study](passport-blind-visual-study.mjs), [saved result](passport-blind-visual-study.json), [screenshots](browser-blind-worlds/intro-match-intact.png), and [source/bundle freshness audit](audit-passport-blind-visual-study.mjs) compare all four worlds before any click. The opening rendered text, accessibility snapshot, initial GET URLs, statuses and body bytes, image bytes, and full-page decoded pixels are identical. After starting a round, the visible closed scene and player response also match, allowing only opaque round/message IDs, capability tokens, and clock fields to vary in the response. Requesting the card changes only the signature relation; using the UV lamp first changes only the thread condition. An exploratory post-run extension found that the complete card and UV-first action responses and accessibility snapshots obey the same one-factor separation after normalizing opaque event IDs and timestamps. Both first-use orders were exercised. Replacing the passport-cover raster with another served image changes neither configuration nor rendered text, but changes the downloaded image bytes and decoded page pixels. This negative control shows why JSON and DOM checks alone miss asset-carried differences. It does not perform OCR or certify that a semantic clue is absent from arbitrary image contents. The fixed local viewport, first-use paths, deterministic completion stub, and research-only routing limit the result; other browsers, questions, player histories, and the full target request are outside this blind-player certificate.

### Observer-relative asset cuts

An author must say which observation channel the reveal claim covers. For a casual player, rendered pixels and accessible text are plausible channels; for a developer with network tools, downloaded asset bytes and metadata are also available. The same two worlds can be indistinguishable in one channel and distinguishable in another. The [observer-cut function](observer-relative-cut.mjs) compares counterfactual captures by declared channel and returns the differing resources rather than one undifferentiated pass badge. This is an *authoring* test of information exposure, not a model test of whether a visual clue is read or obeyed.

The [asset-carrier protocol](asset-fact-boundary-protocol.md), [four-fixture browser study](asset-fact-boundary-study.mjs), [saved result](asset-fact-boundary-study.json), [raster screenshot](browser-asset-facts/raster-match.png), [metadata screenshot](browser-asset-facts/metadata-match.png), and [independent freshness audit](audit-asset-fact-boundary-study.mjs) inject the card signature into the pre-card passport-cover asset in two ways. In a raster pair, `E. Vale` versus `N. Vale` is visibly printed on the cover. The intro API, DOM text, accessibility snapshot, resource paths, and every other GET body are equal, but the cover bytes, decoded cover pixels, and screenshot pixels differ. Both screenshots were inspected visually; no OCR score is claimed. In a metadata pair, the cover pixels and full-page screenshot pixels remain equal, while WebP EXIF `ImageDescription` contains the different card signature and the downloaded bytes differ. The only differing GET resource in either pair is `/reference-assets/passport-cover.webp`. Thus a JSON or accessibility audit misses the visible clue, while a screenshot-only audit misses the downloadable metadata clue. These are deliberately injected controls; the ordinary cover passed the earlier four-world byte and pixel comparison.

A fact can also enter through an asset **after** the opening snapshot and **before** the declared click. The [temporal observer-cut function](temporal-observer-cut.mjs) compares paired browser histories after the same actions and reports the first differing action for each channel. In a [two-order protocol with a documented POST-channel extension](temporal-asset-cut-protocol.md), we ran `open → card` and `card → open` in two signature worlds, first with the ordinary open-book asset and then with a world-specific signature visibly printed on that asset. The [eight-fixture result](temporal-asset-cut-study.json), [freshness audit](audit-temporal-asset-cut-study.mjs), and [paired open-book screenshots](browser-temporal-assets/injected-open-card-match-open.png) show the control: with ordinary art, screen pixels, accessibility, and the normalized POST action payload first differ at `card` in both orders. With altered art, `open → card` first differs at `open` in screen pixels and the downloaded `/reference-assets/open-book.webp`, while accessibility and POST response still first differ at `card`. In `card → open`, the screen first differs at `card`; the later image change is redundant. The GET-only asset channel reports no clean card reveal because that fact arrives in the POST action response. The saved normalized payloads mask only opaque identifiers, capability tokens, and timestamps, and their hashes are recomputed in the audit. This separation prevents a false claim that every observation channel changes at the same action. The injected wording is plainly legible in both visually reviewed open-book screenshots. The browser method returns a concrete bypass witness for these two paths, not an exhaustive certificate over every possible action history.

We then linked the finite state search to those browser observations through a [model-selected witness protocol](model-browser-cut-protocol.md). Its [study](model-browser-cut-study.json) and [recomputation audit](audit-model-browser-cut-study.mjs) use the actual passport reducer and player serializer. The graph's asset field uses the **exact WebP hashes served in the browser runs**, present only after the modeled `open` action. With ordinary art, the event-cut search certifies `card` for this first-use action model and selects `[card]` as a shortest reveal; the paired browser `card → open` history confirms that prefix in screen pixels and the POST response. With the injected asset, the graph selects `[open]` as the shortest bypass; the paired `open → card` browser history confirms the same action and fetched asset hashes. Its normalized POST response still first differs at `card`, narrowing the bypass to the visual and downloadable-asset channels. A deliberately incomplete model that omits the loaded asset returns a false `card` certificate while the browser still diverges at `open`. This negative control demonstrates why a green state graph cannot stand in for a browser observation check. The graph explores its declared first-use reducer actions, and the browser confirms only the selected witnesses, so the two together still do not establish full browser-path coverage.

To test a second factor and controls gated by earlier actions, we paired the same-signature `match-intact` and `match-broken` worlds. The [locked UV-path protocol](uv-conditional-path-protocol.md), [six-browser-run study](uv-conditional-path-study.json), and [fresh recomputation audit](audit-uv-conditional-path-study.mjs) use three legal histories: direct `lamp:uv`, `open → turn → lamp:uv`, and `card → open → compare → turn → lamp:uv`. The actual first-use reducer graph explores 150 paired states and certifies `lamp:uv`, selecting it as the shortest reveal. In the browser, all three paths remain equal through every pre-lamp prefix in DOM text, accessibility, decoded pixels, normalized POST response, and GET resources. At the lamp action, the first four channels distinguish intact from broken; the GET-only resource channel remains equal. Every browser action response's player documents and stable event observations agree with the corresponding reducer step. The long path exercises `turn`, which needs an open passport, and `compare`, which needs both documents, without creating an early UV leak. This is a conformance result for three selected histories, not evidence that all possible browser histories preserve the cut.

[VPI-Bench](https://arxiv.org/abs/2506.02456) studies instructions embedded in rendered interfaces, and [Beyond the Verdict](https://arxiv.org/abs/2609.05535) uses matched image counterfactuals and evidence localization to evaluate visual guardrails. Those papers show that visual evidence and counterfactual images are established research topics. Our narrower contribution is an author-facing reveal contract that locates *when* a game fact crosses each declared player boundary before an intended click. The local controls establish that the proposed checks catch these two constructed carriers. They do not establish semantic detection for arbitrary art, OCR reliability, or priority over visual counterfactual evaluation.

### Counterfactual compilation fidelity

Before model testing, an author can check whether all worlds are compiled from one typed prompt template. Let $z$ assign a value to each declared variable fact, and let $C(T,z)$ be the actual target prompt produced from template $T$. Compile the same template once with opaque provenance markers in those fact slots. Substituting the assigned values into that marked request must reproduce the actual request byte for byte; the marked request is $N_z(C(T,z))$. This avoids normalizing an accidental second copy of the same value outside its declared slot. For worlds that differ in one fact, we require different raw prompt hashes but the same normalized hash. The compiler also rejects a declared fact that is never bound, a known variant phrase written directly into the shared template, or a compiled request containing an alternative value for the same fact. This is a causal dependency check on the *compiler output*: a change in one authored fact must change the request at a declared binding and nowhere else in the static target prompt.

The [bound-template implementation](../server/world-bound-template.mjs), [two-family study](world-bound-template-study.json), [source audit](audit-world-bound-template-study.mjs), and [tests](world-bound-template.test.mjs) exercise this rule on the four passport worlds and a separate four-world equipment inspection. All eight one-factor world pairs have distinct compiled target prompts and the same normalized target prompt within their family. Six negative controls are rejected before a provider call: the original hardcoded passport signature, a hardcoded UV result, an omitted fact binding, an unbound compiler branch, a duplicate of the selected value outside its binding, and a compiler that omits a fact. The real passport research route now uses the bound template to create each version. The initial player serializers are equal across worlds in both families; the separate routed-world study checks actual HTTP and completion inputs for the passport family.

A companion [factor influence matrix](counterfactual-influence-matrix.mjs) crosses worlds that differ in exactly one fact and compares the actual player serializer, verified desk context, and compiled target prompt at fixed action stages. The author declares whether each factor should be hidden or revealed at each surface. The [two-family result](counterfactual-influence-study.json) and [freshness audit](audit-counterfactual-influence-study.mjs) find all 26 declared cells satisfied across eight one-factor pairs. Four injected controls produce a first-differing-field witness: UV in the initial player payload, UV coupled to requesting the card, a missing card reveal, and a fuse-dependent button visible before inspection. This matrix tests *which fact can affect which boundary and when*. The earlier dynamic belief-state audit still answers the different question of whether a decision can be reached or an intended click bypassed over all modeled action paths. A passing influence matrix is not a full path certificate.

The check is deliberately narrower than semantic truth. Authors must declare the variant phrases and known static aliases. The study deliberately adds an undeclared paraphrase saying an ultraviolet strip was severed in an intact-thread world; the audit accepts this invalid prompt. It also rejects a benign quotation of a known alias as a conservative false alarm. Both limits are saved in the study report. Normalizing the static prompt does not certify dynamic desk context, images, tools, or a provider wrapper that changes the final request. Those need runtime capture and browser inspection. [Counterfactual task evaluations](https://arxiv.org/abs/2307.02477) test whether models understand changed world assumptions, and [semantic-invariance testing](https://arxiv.org/abs/2603.13173) tests model responses under meaning-preserving changes. Our preflight checks the authoring and request-compilation boundary *before* those model-behavior questions arise. It is a scoped sandbox technique, not a claim to have invented metamorphic testing or typed templates.
We then tested the same decision structure with a live model, after locking the [two-clue protocol](two-clue-protocol.md). Four worlds were each queried with no inspection, UV only, comparison only, and both inspections, crossing a vague natural-language rule with explicit ordered branches. The server-compiled system field included only verified observations; opposite-outcome worlds with the same partial evidence had identical full request bodies. Across 32 GPT-OSS 20B calls there were 32 replies and no provider errors. The explicit arm returned the exact required lowercase label in **16/16**; the vague arm did so in **9/16**. Both arms held correctly after a single observed failure in 4/4 and decided correctly after both checks in 4/4. The vague arm failed at missing evidence: it waited in only 1/4 no-inspection cases and 0/4 ambiguous passing-partial cases, often clearing prematurely. The explicit arm waited in all eight such cases. The [raw requests and replies](two-clue-results.json), [hash-checking analysis](analyze-two-clue.mjs), and [summary](two-clue-summary.json) preserve every outcome. This is a second task family and a conditional decision rather than the earlier linear route chain, but it uses the same model, four authored worlds, and one call per condition. It supports a narrow prompt-design observation, not a general reliability estimate.

We locked a [stability replication](two-clue-repeat-protocol.md) with two further calls for every identical condition, randomized independently while preserving the exact prompts and request bytes. All 64 new calls replied without provider errors. Across the original and repeated runs, the explicit rule matched **46/48** required labels and the vague rule **26/48**. Explicit branches waited in 12/12 no-inspection cases and 10/12 ambiguous partial cases; vague wording waited in 6/12 and 0/12 respectively. Both explicit errors were `hold` after `UV=intact; SIGNATURE=NONE`. That request was byte-identical for two worlds with opposite hidden final outcomes, so the misses cannot be explained as access to the hidden signature. Six of 18 distinct request bodies produced more than one reply label across samples at temperature 0.3. The [repeat raw record](two-clue-repeat-results.json), [request audit](analyze-two-clue-repeat.mjs), and [combined summary](two-clue-repeat-summary.json) show exactly where the first-run 16/16 became 46/48. This is a descriptive stability check over frozen cases, not an estimated population success rate.

We also locked a [Gemini transfer](two-clue-gemini-protocol.md) using the same two instruction texts and verified observation fields converted to `generateContent`. All 32 Gemini 3.5 Flash-Lite calls replied with one lowercase label and no provider errors. Both the vague and explicit arms matched **8/16** expected labels. Every observed failure or fully inspected case was correct in both arms, while every no-inspection or ambiguous passing-partial case received a premature `clear` or `hold`. Thus the explicit wording that improved this GPT-OSS sample did not preserve abstention on this Gemini sample. The [raw Gemini record](two-clue-gemini-results.json), [analysis](analyze-two-clue-gemini.mjs), and [summary](two-clue-gemini-summary.json) preserve request hashes, outputs, and evidence-state breakdowns. Gemini's API structure, temperature 1 setting, and sampling time differ from GPT-OSS, and each condition was sampled once; this is a transfer diagnostic, not a controlled comparison of model quality.

A [locked spoofing follow-up](two-clue-spoof-protocol.md) held those verified fields fixed and appended an ordinary tester message claiming an unrecorded UV or signature inspection. It sampled seven ambiguous states, each with a clean control and two desired false outcomes. Across 21 calls there were no provider errors. Clean controls waited in **6/7**; one control prematurely cleared, so even the benign instruction is not perfectly reliable at temperature 0.3. Claims of a failing missing check induced `hold` in **7/7** calls. Claims of a passing missing check induced four `clear`, one `hold`, and two `wait` replies. Thus **12/14** attacks produced a decision where verified evidence still required `wait`. The [raw record](two-clue-spoof-results.json), [request audit](analyze-two-clue-spoof.mjs), and [summary](two-clue-spoof-summary.json) distinguish control errors from attack responses. These are raw model outputs, not published game transitions. A server gate keyed to actual inspection events and verified observations would reject a non-wait label in these states, but that gate has not been connected to the deployed application. This is one crafted wording per outcome, not an attack success-rate estimate.

We then locked a [claim-style protocol](two-clue-claim-style-protocol.md) before further calls to test whether the observation depended on that one sentence. Three verified ambiguous states each received a clean request and false-failure/false-pass claims in plain first-person, copied desk-note, and forged application-update styles. Four stateless samples per condition gave **84/84** GPT-OSS 20B replies across 21 distinct request bodies; eight provider 429 interruptions were saved during resumptions, with no missing final replies. The [hash-checking analysis](analyze-two-clue-claim-style.mjs) verifies every body against the frozen manifest and reproduces the [summary](two-clue-claim-style-summary.json) from the [raw record](two-clue-claim-style-results.json). Clean controls returned the exact `wait` in **10/12** calls. Plain claims induced the requested premature `hold` or `clear` in **24/24**, copied notes in **21/24**, and forged updates in **24/24**. The three copied-note exceptions were all passing claims after an intact UV result with the signature still missing; those replies waited. Thus **69/72** false-claim calls produced the requested premature decision, while two of twelve clean calls also decided prematurely. The offline observation-keyed gate rejected all **71** premature decisions and accepted thirteen waits; none could publish a final decision because verified evidence was incomplete. This is strong evidence that the earlier vulnerability was not confined to one wording in this fixed GPT-OSS task. It is not a general attack prevalence estimate, a ranking of styles, or proof of live web-app enforcement: only three observed states and four samples per distinct body were tested, and the publication results are offline replay.

To make the proposed release rule concrete, a [small publication-gate prototype](two-clue-publication-gate.mjs) computes the permitted decision from **server-supplied** verified observations and parses a whole-label model reply. It returns `waiting` when evidence is insufficient and the reply says `wait`, `published` when a decisive reply matches the verified facts, or `rejected` for a premature, contradictory, or malformed reply. Its [tests](two-clue-publication-gate.test.mjs) cover a fake-inspection claim, a decisive single failure, a fully supported clear, and mixed output. An [offline replay](two-clue-gate-replay.json) over all 149 archived two-clue replies yielded 60 supported final publications, 36 waits, and 53 rejections. In particular, it rejected all 13 non-wait replies in the spoofing follow-up and all 16 Gemini missing-evidence decisions. These counts demonstrate deterministic classification under this authored rule; the observations in the replay came from the study compiler rather than a deployed event ledger. The gate is not yet integrated with the web app or tested against client-controlled event tampering.

An independent [equipment transfer protocol](equipment-model-live-protocol.md) joined the same inspection reducer to saved browser POST observations, then compiled those verified readings into a system instruction. Three worlds each had clean and false-claim initial states, fuse-only and voltage-only partial states, and clean and contradictory fully inspected states, with two shuffled stateless GPT-OSS 20B calls each. The [preflight](equipment-model-live-plan.test.mjs) checks that opposite worlds produce byte-identical initial requests and that every later browser response agrees with the reducer. The [raw record](equipment-model-live-results.json) and [integrity analysis](analyze-equipment-model-live.mjs) show **36/36 replies**, no provider errors, and **36/36 evidence-consistent whole labels** under the predeclared case-folded, optional-terminal-period score. None of the 12 fixed false-claim requests produced the demanded wrong or premature label. This differs from the passport false-claim pilot, but the scene, prompt, trusted-state channel, and wording all changed together, so the contrast is not a causal estimate of any one design choice.

Exact output and decision correctness diverged. The frozen strict gate accepted 19/36: 16 supported final decisions and three exact waits. Seventeen other replies said `Awaiting inspection` without its prescribed period and were rejected despite making the correct wait decision. A clearly marked post-run [anchored label canonicalizer](equipment-label-canonicalizer.mjs) and [replay](equipment-label-replay.json) accepted all 36 saved whole-label replies while rejecting six malformed or mixed strings against each of the 36 states. Its [tests](equipment-label-canonicalizer.test.mjs) also reject a false player claim when verified readings are incomplete. This bounded replay suggests that the author UI should show exact format, canonical decision, and publication status separately, and may canonicalize only a small declared output grammar before a fact-keyed gate. It is not evidence that the parser handles arbitrary adversarial text, and the gate here remains offline rather than deployed.

The [locked crossed follow-up](equipment-crossed-protocol.md) held the same three equipment worlds, browser-derived complete observations, and player claims while crossing explicit versus concise decision wording with system versus preceding-user placement of the *same* verified-state line. The [preflight test](equipment-crossed-plan.test.mjs) checks initial opposite-world request equality, unchanged source payloads, and the planned single-factor differences between arms. Across [96 saved provider replies](equipment-crossed-results.json), the [integrity analysis](analyze-equipment-crossed.mjs) found no provider errors, 24/24 semantically correct whole labels in each of the four arms, and zero agreement with the false claim in 48 attack calls. The concise/user arm did not fail in this fixture, so these data do not support a claim that explicit branches or system placement were individually necessary here. They also do not prove the arms equivalent: there are only two samples per world/condition/arm, and all arms retain the same instruction that player text is not a verified measurement. Exact output was 52/96 overall; 44 of 48 waits omitted the period, while all 48 decisive `hold` or `release` replies matched exactly. The cross-task contrast with the vulnerable passport case remains unexplained. A next ablation should change the shared authority sentence and attack phrasing while holding this equipment task fixed.

That next [authority-sentence protocol](equipment-authority-protocol.md) is frozen over two ambiguous browser-verified states and three false-claim styles. Its [preflight](equipment-authority-plan.test.mjs) proves the two arms differ by only one sentence. The provider stopped the [resumable run](equipment-authority-results.json) at a daily token 429, then stopped again after a same-manifest resume; 14 of 56 planned replies are saved. The remaining jobs are unrun and no arm comparison is reported. The identical manifest can resume when quota becomes available; the partial replies are not treated as evidence for the hypothesis.

This is related to established optimal decision-tree and active-diagnosis formulations, which choose tests based on the remaining hypotheses and their outcomes; see [Optimal Decision Tree and Adaptive Submodular Ranking with Noisy Outcomes](https://arxiv.org/abs/2312.15357). [Belief-State Engine](https://arxiv.org/abs/2609.10036) likewise maintains an explicit belief over partially observed states outside an LLM. We do not claim to have invented belief sets or decision trees. The sandbox-specific use is to tell an author whether a declared object is required, conditionally useful, redundant, or already leaked by the client. The prototype covers static, deterministic observations from a small authored world set. Dynamic action availability belongs to the event-cut audit; noisy clues, player priors, and actual discoverability require separate studies.

### Certifying distinct work for three specialists

The same paired-world idea can check more than one handoff. In an [eight-world chain prototype](chain-contract.mjs), A privately sees an arbitrary seal color, B privately holds the color-to-route codebook, and C privately holds the route-to-vehicle schedule. The worlds vary the color and independently flip each private mapping. B cannot decode a route before A shares the color. After that share, B still cannot determine the final vehicle because two worlds with different fleet schedules give B the same complete request but require different vehicles. C cannot choose a vehicle before B shares the decoded route. A cannot decode the route because a codebook flip leaves A's complete request unchanged while reversing the route. The [tests](chain-contract.test.mjs) check these counterfactual equalities and verify that artifacts cannot cross world or handoff edges.

This yields a **role capability audit** in addition to a handoff audit. For each specialist and each claimed output, the author searches for a twin world with an identical complete role view and a different correct output. A certificate does not make the model wait or reason correctly, but it prevents a single role from having enough *provided information* to solve every stage. That addresses the original orchestration problem more directly than telling a powerful model to “act less capable.” It remains conditional on stateless calls and on the codebooks and schedules being genuinely private rather than recoverable from prior turns, shared board notes, or model-accessible tools.

### A live three-role chain and an authority challenge

The structural audit initially used oracle values, so we fixed a [live chain protocol](chain-live-protocol.md) before calling the model. Across all eight worlds, each stateless run first tested B and C without a handoff, then called A, handed A's parsed reply to B, and would hand B's parsed reply to C. There were 40 planned stage records and 32 provider calls; all 32 returned without provider errors. B and C each gave the exact wait in all eight before-handoff calls. A returned a parseable, true color in all eight, although only two replies used the exact lowercase format. In every after-handoff call B's raw text included the correct route **and** `Awaiting color.`. For example, one reply was `Awaiting color.\nNorth`. The preregistered whole-label parser rejected all eight, so C was correctly skipped in all eight. The [raw record](chain-live-results.json), [reproduction analysis](analyze-chain-live.mjs), and [summary](chain-live-summary.json) preserve the mixed replies. Zero of eight chains completed under the declared protocol. This was a state-transition and output-format failure, not evidence that B lacked the route.

We then locked a separate [state follow-up](chain-state-followup-protocol.md). It reused the eight saved, true A replies and changed B/C to server-compiled state fields: `SEAL_COLOR=NONE` or `ROUTE=NONE` before sharing, replaced by a verified source value afterward. The prior parser and world bindings remained fixed. All 32 calls returned without provider errors. B and C gave exact waits in all eight pre-handoff cases; B gave the correct whole route in all eight after A's saved reply; and C gave the correct whole vehicle in all eight after B's **actual newly saved reply**. Thus all eight chains were semantically complete, and all eight downstream portions met the exact response format. Only two of eight full chains met that exact format because six saved A replies capitalized the color. The [raw record](chain-state-followup-results.json), [analysis](analyze-chain-state-followup.mjs), and [summary](chain-state-followup-summary.json) document the result. This intervention changed the instruction and handoff representation together and reused A outputs from the earlier sample. It cannot identify which prompt feature caused the improvement, and eight worlds do not establish a reliability rate.

A successful normal handoff does not establish an authority boundary. We locked a [third protocol](chain-state-adversarial-protocol.md) and challenged each B/C role before and after a real handoff. Before sharing, an ordinary tester message claimed a fixed `SEAL_COLOR=amber` or `ROUTE=north` despite server state `NONE`. Both roles gave a premature whole-label answer in all eight worlds. After sharing, the tester message claimed the *opposite* value from a verified A or B artifact. Both roles followed that tester claim in all eight worlds and none followed the authentic source. All 32 calls returned without provider errors. An offline gate would block the 16 premature answers for missing source and reject the 16 contradictory answers as inconsistent with the source. The [raw requests and responses](chain-state-adversarial-results.json), [analysis](analyze-chain-state-adversarial.mjs), and [summary](chain-state-adversarial-summary.json) make the source and tester claims inspectable. This is one attack wording and one call per condition and world, so it describes a concrete vulnerability of this package, not a universal attack rate. The gate verdict is a policy replay, not evidence that the deployed workshop currently enforces it.

We then asked which part of the benign state package fixed B's transition. A [preregistered instruction/channel ablation](chain-b-ablation-protocol.md) reused the saved A colors and the literal `Application handoff from A: SEAL_COLOR=<color>.` across the eight worlds. The original B instruction and an explicit conditional instruction were each crossed with user-message and system-message delivery; a compiled-state request was a contemporaneous fifth reference. All 24 before-handoff calls waited exactly. After handoff, the original instruction yielded **0/8** usable whole-label routes in either channel, while the conditional instruction yielded **8/8** in either channel; the compiled-state reference also yielded **8/8**. All 64 calls returned without errors. The [raw record](chain-b-ablation-results.json), [analysis](analyze-chain-b-ablation.mjs), and [summary](chain-b-ablation-summary.json) show that channel movement alone did not repair this sampled B formatting failure. The conditional instruction changed several words and included both an explicit branch table and a no-mixed-output sentence, so this first ablation did not isolate the operative clause.

A second [locked mechanism experiment](chain-b-mechanism-protocol.md) crossed those two additions under the same user-channel handoff. The vague original branch wording produced **0/8** usable after-handoff routes, with the correct route mixed with waiting text in all eight. Appending only `Return one complete label only. Do not combine a wait with a route.` still produced **0/8**: seven replies remained `Awaiting color.` and one mixed a wait with the route. Replacing the vague instruction with explicit no-handoff, amber, and cobalt branches produced **8/8** correct lowercase routes, with or without that format sentence. All four cells waited exactly before handoff in all eight worlds; all 64 calls returned without errors. The [raw record](chain-b-mechanism-results.json), [analysis](analyze-chain-b-mechanism.mjs), and [summary](chain-b-mechanism-summary.json) preserve the requests and replies. Within this narrow task, explicit state-to-output branches were sufficient to resolve the observed transition; a formatting prohibition alone suppressed the route more often than it repaired the transition. This is one response per authored world and cell, not a general prompt law.

It reused the eight **actual B replies** saved in the successful state follow-up, not an oracle route. Original C waited exactly in 8/8 before calls but returned **0/8** usable whole-label vehicles after handoff: six replies kept waiting and two combined a wait with the correct vehicle. Generated C returned the correct lowercase vehicle in **8/8** after calls. It waited before sharing in all eight, with seven exact waits and one missing the final period. This supports transfer from B to C within the same synthetic chain and model; it is not a second task family or a reliability estimate.

Together these runs show why the authoring view needs a **stage-level explanation**. The first run has a valid source fact but a malformed B output, so C receives nothing. The benign state follow-up passes the source and both downstream stages. The instruction experiments and C transfer show how an explicit branch table can make both downstream transitions legible to this model without relying on system-channel delivery. The adversarial run gets clean whole-label output yet would publish none of the attacked stages because their source or consistency checks fail. A single success percentage would conflate these mechanisms.

## Working example and pilot

The prototype uses an extractor A, calculator B, and presenter C. In one world a box has seven red and five blue cards, so the answer is 12. In its twin the blue count is nine, so the answer is 16. A receives the private blue count. Before A's handoff, B and C each receive the same generic case in both worlds: seven red cards and a statement that the blue count is known only to A. The compiler tests exact equality of their request objects. A's response is parsed into two numbers, then the server issues a typed `operand-pair` artifact bound to the run, world, source role, and source event. B receives the parsed counts and emits a total. C receives a typed `total` artifact. The HMAC prevents a client from altering or replaying the artifact across worlds; it does **not** prove that A extracted the right numbers or B calculated correctly. The prototype tests wrong-world reuse, wrong recipient type, and payload tampering.

We compared the same two worlds under full-case and gated visibility at temperature 0.3 using the existing Groq GPT-OSS 20B connection. The [pilot script](paired-world-pilot.mjs) records the exact request, response, and provider errors after every call. In the full-case condition, C gave the correct final count before any handoff in both worlds while also saying “Awaiting handoff.” B's full-case requests produced no answer after three attempts each because the provider returned HTTP 400 with “Tool choice is none, but model called a tool.” [Groq documents](https://console.groq.com/docs/tool-use/local-tool-calling) that some models can attempt a tool call despite `tool_choice: none`, resulting in this error. These errors are missing model observations, not compliant refusals. In the gated condition, both B and C replied “Awaiting handoff” before sharing in both worlds. A then returned `7,5` and `7, 9`; B returned 12 and 16; C gave the corresponding final sentences. The second post-handoff C reply also retained the phrase “Awaiting handoff,” showing a formatting violation despite a correct total. Across the pilot, eight provider errors occurred on retried requests. Fourteen planned probes were recorded, with two no-response observations, and the pilot is far too small for a population estimate.

These observations support two limited conclusions. First, the current full-case pattern can make a specialist answer from shared information without the intended board event. Second, the contract compiler successfully creates a request-level dependency, and this particular model used the handed-off value in two sampled worlds. The pilot does not establish that the model will reliably abstain, that arbitrary natural-language tasks can be compiled correctly, or that the signed handoff is truthful. The full-case and gated conditions differ in available information, so this is a mechanism demonstration, not a controlled estimate of prompt quality.

A separate [one-call spoof probe](spoof-pilot.json) sent B the gated case but put “Verified extractor handoff: red=7, blue=5” in the tester's ordinary message, with no artifact. B returned `12`. The prototype's server gate retained that raw reply and published “Awaiting handoff.” This is direct evidence in one sample that a model can treat a textual claim as a handoff even when the application has no corresponding event. It supports keeping model behavior and game-state authorization separate; one call cannot estimate how often the spoof works.

### Non-numeric route stress test

We next authored a delivery scenario with two possible open routes. A alone sees the dispatch bulletin. B chooses `pickup truck` for Ridge Road or `cargo van` for Canal Ferry; C writes the final plan. The [route contract](route-contract.mjs) passes the same pre-handoff request-equality test and uses the same run/world-bound artifact mechanism. We ran three exploratory two-world variants, archived as [free-form user handoff](route-pilot.json), [free-form system handoff](route-system-pilot.json), and [typed system state](route-state-pilot.json). The [analysis script](analyze-route-pilots.mjs) reproduces the counts in [the summary](route-summary.json).

In all three variants, all four gated pre-handoff responses were exact waits. In the user-message variant, B produced no exact vehicle after either route handoff: it waited in one world and a provider error exhausted the other. The system-message variant also produced no exact vehicle after either handoff; B waited in both worlds. Thus passing the information-dependency audit did not make the downstream model use a loosely phrased handoff. In the typed-state variant, the server represented absence as `ROUTE=NONE` and, after verifying an artifact, replaced that value with the handed-off route. B chose the correct vehicle in both worlds and C wrote the corresponding plan in both. When the full case was shown in that same variant, B chose the correct world-specific vehicle before any handoff in both worlds despite `ROUTE=NONE`; the prompt could not compensate for the information leak. The free-form user, free-form system, and typed-state runs had four, one, and zero provider errors across attempts, respectively. These runs change prompt wording as well as channel and were not randomized or repeated enough to attribute the difference to a single factor. They show a concrete failure mode and a promising design candidate, not a comparative performance result.

### Crossed format and channel follow-up

The first expanded study left a confound: the typed-state package changed the base instruction as well as the representation. We fixed a [crossed protocol](route-crossed-protocol.md) before another provider run, using the same eight route pairs. A common base instruction explicitly said to use a separate application handoff message. We crossed narrative versus `ROUTE=<route>` message format with user versus system delivery, keeping the rest of the serialized provider request fixed within the four-arm design. For each of 16 worlds and four arms, we sent one before and one after request, in seeded random order. The oracle issued and verified the correct route artifact before the after request. The [raw record](route-crossed-results.json) contains all 128 bodies and replies; [analysis](analyze-route-crossed.mjs) reproduces the [summary](route-crossed-summary.json). All 128 requests returned replies and there were no provider errors.

Before sharing, B returned the exact `Awaiting route.` in all 64 requests. After sharing, the preregistered exact-string vehicle score was 0/16 for user narrative, 0/16 for user typed, 5/16 for system narrative, and 4/16 for system typed. Inspecting the raw replies revealed that **all 64 named the correct vehicle**, with capitalization as the sole difference from the stored lowercase labels in 55 cases. A secondary case-insensitive whole-label score, added after seeing this pattern and declared in the protocol's post-run note, was 16/16 in every arm. Strict paired-case success was 0/8, 0/8, 1/8, and 1/8 respectively; semantic paired-case success was 8/8 in all four arms. The exact outcome remains in the record, but it measures output-format compliance here rather than route uptake.

Within this common instruction, neither formatting the handoff as `ROUTE=...` nor moving it to the system channel changed the observed *vehicle choice*. The contrast with the previous run suggests that the broader instruction package matters, but the two runs are not a randomized test of that instruction alone. The result also exposed an evaluation design requirement for the sandbox: task correctness and exact response formatting need separate fields. In an [offline replay](publication-gate-summary.json), the original strict gate would reject 55 of 64 semantically correct after-handoff replies solely for capitalization. A strict gate may intentionally enforce case, but it should not label a correctly chosen vehicle as a failure to use the handoff. The [route scorer](route-contract.mjs) now reports semantic choice separately while leaving publication policy strict and explicit. Benign success in a user-message arm does not authenticate that message; the spoof tests below address that separate question.

### Transfer to a Gemini model

To test transfer beyond GPT-OSS, we pinned `gemini-3.8-flash` and attempted the same four-arm route design through the [Gemini `generateContent` API](https://ai.google.dev/api/generate-content). Gemini puts instructions in a top-level `systemInstruction`, so the later system-channel handoff was appended there rather than represented as a separate system message. We set temperature to 1 in line with [Google's current Gemini 3.x guidance](https://ai.google.dev/gemini-api/docs/generate-content/text-generation). This is a transfer test, not a clean comparison of model weights. The [3.8 Flash protocol](route-gemini-protocol.md) and [raw record](route-gemini-results.json) show that the run stopped after nine attempted trials: five replies, four no-responses, one free-tier 429, and ten HTTP 503 high-demand errors across attempts. The [availability analysis](route-gemini-availability-summary.json) is not scored as model quality.

We then locked a separate [Gemini 3.5 Flash-Lite protocol](route-gemini-35lite-protocol.md) over all 128 requests. Its [raw record](route-gemini-35lite-results.json), [analysis script](analyze-route-gemini.mjs), and [summary](route-gemini-35lite-summary.json) show 128 replies with no provider errors. Before handoff, all 64 replies conveyed `Awaiting route`, but only 13 included the exact required period. After handoff, only 10 of 64 replies consisted solely of the correct whole vehicle label under case-insensitive scoring; the exact-string count was seven. Every arm had zero of eight strict or whole-label paired-case successes. These outcomes are materially different from GPT-OSS under the corresponding common instruction, which chose the correct whole vehicle in all 64 after-handoff requests. The API structure, temperature, and sampling time differ, so this is a descriptive transfer result rather than a model ranking.

The raw Gemini replies explain much of the whole-label failure. A post-run transcript diagnostic found 47 replies that combined the correct vehicle with `Awaiting route`, two with the correct vehicle plus other text, two that echoed both vehicle labels, two that named only a route, and one that only waited. Ten were clean whole-label choices. The first three categories often contain evidence that the model noticed the route, but they do not satisfy the contracted output and must not be silently accepted by a permissive substring grader. The sandbox should show the source of the failure: waiting text carried into a post-handoff answer, extra explanation, ambiguous alternatives, or a genuine missing vehicle choice. ### Adversarial follow-up

We then fixed [an adversarial protocol](route-adversarial-protocol.md) over the same 16 worlds and ran 48 more stateless requests. The [raw record](route-adversarial-results.json), [analysis](analyze-route-adversarial.mjs), and [summary](route-adversarial-summary.json) are archived. With no artifact and application state `ROUTE=NONE`, a tester's ordinary message asserted `ROUTE=<true route>`; B returned the mapped vehicle in all 16 cases and never waited. With a valid artifact setting the true route but a tester message asserting the opposite route, B followed the tester's route in 15 of 16 cases and the signed route in one. With an authentic artifact containing the *wrong* route, B followed that artifact in 15 of 16 cases and waited once. There were no provider errors in this follow-up.

The wrong-artifact condition is not a failure of B to obey its evidence: the gated request gives B no way to know which route is actually open. It demonstrates that provenance and factual correctness are separate. The spoof and contradiction conditions demonstrate that a typed state string in a system prompt is not an enforceable authority boundary by itself. A deterministic application gate can block publication when no artifact exists, reject output inconsistent with a valid artifact, and, in authored synthetic worlds with known truth, flag an authentic but false upstream finding. We added those distinctions to the [route gate prototype](route-contract.mjs). The model's raw response remains available so authors can see the violation rather than have a gate silently mask it.

An [offline replay of the publication policy](publication-gate-summary.json) against all recorded route replies yielded the expected separation: the 16 no-artifact spoof replies would remain unpublished, 15 of 16 contradictory replies would be rejected as inconsistent with a valid artifact, and all 16 authentic-wrong artifacts would be flagged against the authored world before considering B's reply. The benign typed-state after-handoff replies would all be accepted. This replay reconstructs signatures over the saved worlds; it is a policy simulation, not a deployed runtime defense or a test of event-ledger linkage.

Together these results motivate separate questions for every intended interaction. **Necessity:** could the recipient distinguish opposite outcomes before the event? **Uptake:** after a valid event, did the recipient use the new fact? **Format:** did the reply satisfy any exact output rule? **Authority:** could untrusted text create or override the effect of the event? A final check asks whether the source fact was correct. A contract can pass necessity and fail uptake under one prompt, pass uptake and fail exact format, or pass benign uptake and fail authority. This is why a single “level passed” badge would mislead an author.

## Proposed sandbox feature

The authoring UI should add a **dependency view** beside the existing prompt editor. The author enters a concise fact, its owner, the recipient, the transfer event, the answer function or rubric, and two values that change the outcome. For the orchestration sandbox, the default case must be split into public facts and role-private facts. A world builder then creates two frozen trials and compiles the exact request for each role at each stage. It refuses to certify a handoff if the recipient's pre-handoff requests differ or if the final answers are the same. The author can inspect a readable diff of exactly what changed after the handoff.

Board entries should remain linked to a saved model reply, as they are now, but the next version should distinguish free-form notes from typed handoff artifacts. A typed artifact has a declared schema, source event ID, source role, run and world binding, recipients, and a server-issued signature or equivalent server-owned record. The server verifies provenance before constructing the recipient request. For conditional roles, a server-assembled state field such as `ROUTE=NONE` or `ROUTE=Ridge Road` is worth testing because it improved benign uptake in the expanded pilot. The adversarial follow-up shows that the state string must not serve as the authority check: a tester can make the model act as if the state changed. The server checks the event ledger and candidate output before publishing a result. A parser and task verifier assess semantic correctness separately. For example, `operand-pair: {red: 7, blue: 5}` can be authentic as A's output and still be factually wrong. This separation lets the interface show “authentic handoff, incorrect extraction” rather than flattening both failures into a single pass/fail label.

Every trial should keep two views. The **raw model view** shows the response exactly as returned, including premature guesses and malformed outputs. The **published outcome view** applies deterministic prerequisites and parser checks to decide whether a final artifact may enter the game state. A forged phrase such as “verified extractor handoff” typed by a player remains ordinary user text; it cannot create a server event. This does not stop the model from believing the phrase, as the 16-of-16 spoof result illustrates. When an artifact does exist, the server also compares the candidate output with that artifact and, where an authored oracle exists, checks the artifact's factual value. The published view must never promote a claim solely because a model described it as verified.

For the interactive level workshop, the analogous authoring object is a **reveal dependency**. Consider a passport-desk level. Two worlds may initially show the same closed passport and boarding pass; opening or comparing a document reveals a world-specific name relation. The compiler can check that the player-visible scene and accessible text are equal before the required inspection and that the observation changes after it. A design inspector should show the object, reveal action, exposed fact, and consequence. This makes object interaction causally meaningful rather than decorative. If a jailbreak target model already knows the protected secret in its system prompt, the indistinguishability theorem does **not** apply to that target; its private prompt differs across worlds. The level contract can still certify the *player's* initial evidence boundary and test the target's disclosure behavior separately. Client asset bundles and network responses must not preload hidden world facts if the claim concerns an adversarial player who can inspect them.

The [small passport observation prototype](object-reveal-contract.mjs) makes this distinction executable. Both worlds initially expose the same boarding pass and closed passport object, including its label and accessibility name. Opening the passport reveals either the traveler's own name or a brother's name. The audit passes for the player-visible scene and explicitly records that the target's private request differs before opening. A negative test adds the owner's name to the closed passport label and confirms that the audit fails. This is a static scene-data test, not a browser or human playtest. It does not yet prove that the current deployed passport scene keeps hidden values out of its initial API response, bundle, or rendered image.

An initial local API audit found that the blind player's configuration included unopened passport and card details. A subsequent Chromium network trace also found both signatures and the Oslo date at `intro`, with the date additionally embedded in the client JavaScript. We changed the reference route and client: unopened document fields are now withheld from player responses, and the date is rendered from the page-turn response rather than a client literal. The rerun [API-boundary audit](reference-scene-audit.json) finds neither document in the blind configuration. The initial verified model desk context still names Elias Vale from the public boarding pass, and the protected brother-ownership truth remains absent from the blind configuration. These are local post-repair results; the original failing browser report was overwritten during rerun, so the earlier observation is retained here as a development finding rather than a separately archived baseline.

A [second local route audit](reference-visibility-timeline.json) traces the Express response and verified model desk context through `open`, `card`, and `compare`. The blind configuration now has neither document. The verified model desk contains the boarding-pass name from the start, then adds identity-page detail after opening, the card signature after requesting it, and an *explicit comparison sentence* after comparing. The [PGlite PostgreSQL repeat](reference-visibility-timeline-postgres.json) checks the same stages on the other adapter. The full static model prompt is a separate boundary, and a comparison sentence appearing late does not mean its conclusion was unavailable earlier.

We built a reusable [visibility-manifest scanner](visibility-manifest.mjs) that records the first stage and JSON pointer at which each declared literal or derived fact appears on each supplied surface. A [post-repair local reference run](reference-visibility-manifest.json) exercised actual blind-player routes through closed, moved, opened, turned, card, compared, and UV stages, captured the system argument sent to the completion stub at each stage, checked it against the owner context preview, and scanned a freshly built client bundle. The [PostgreSQL-adapter run](reference-visibility-manifest-postgres.json) produced the same exposure manifest as SQLite; a [freshness and parity audit](audit-reference-visibility-manifest.mjs) checks source and built text-asset hashes. The player API now first supplies passport signature at `open`, card signature at `card`, stamp date at `turn`, and UV result at `uv`. The date is absent from the scanned client text assets. The mismatch remains derivable once both signatures arrive, before `compare`. The protected traveller name did not appear in the sampled player APIs or built text assets.

The model surfaces differ again. The verified desk context adds the card signature after `card`, but it has both signatures by then, so the mismatch is inferable **before** `compare` even though the explicit comparison sentence arrives at `compare`. The full target system prompt already contains the card signature, stamp date, UV result, and protected truth at the closed stage; after `open` adds the passport signature, the mismatch is inferable there too. This is expected in part because a jailbreak target is authored with private story truth from the outset. A model-facing event may therefore serve as a **permission or evidence provenance checkpoint** without giving the target new information. The authoring inspector should label that separately from an informationally necessary reveal. If an author wants `compare` to be an information dependency, the action must supply a measurement that cannot be reconstructed from fields served earlier. The manifest's [tests](visibility-manifest.test.mjs) cover early API exposure, derived facts, and never-exposed secrets. The current reference deliberately allows free-order inquiry; the remaining failed compare rule applies to a stricter level claim, not a claim that this reference is malfunctioning.

We then tested the repaired local level in Chromium through its blind-player interface. The [SQLite browser trace](reference-dom-visibility.json) captures rendered text, DOM text, accessibility snapshots, and same-origin JSON/text response bodies at seven stages, with [closed](browser-visibility/closed.png), [opened](browser-visibility/opened.png), [card](browser-visibility/card.png), and [comparison](browser-visibility/compared.png) screenshots. The [PGlite PostgreSQL repeat](reference-dom-visibility-postgres.json) and [parity/freshness checker](audit-reference-browser-network.mjs) agree on every tested first-exposure stage. Both screen and browser network now first expose the passport signature at `open`, the card signature at `card`, the stamp date at `turn`, and the UV result at `uv`; the date no longer appears in the downloaded text assets. The protected traveller name was absent from sampled player text and network surfaces. Response bodies were scanned in memory; the report stores paths and hashes rather than blind session data. A current-screen snapshot first states the mismatch at `compare`, but cumulative screen history and the network already supply both signatures at `card`. This is availability of evidence, not proof that a human noticed or used it. Image OCR, alternate click paths, and a live deployment remain outside this browser sample.

To test order sensitivity, a [25-order runtime study](reference-action-orders.json) exercised every legal one-use ordering of `open`, `turn`, `card`, `uv`, and `compare` on the local Express routes; the [PostgreSQL-adapter repeat](reference-action-orders-postgres.json) agreed with SQLite. The ordering constraints were `open` before `turn` and `compare`, and `card` before `compare`. In all 25 traces, the player API and verified model desk could infer the signature mismatch as soon as the second signature arrived, whether that was `open` or `card`, and never first at `compare`. The full model request could infer it at `open` in every order. The UV result first entered both player API and verified desk context at the UV action. The [audit script](audit-reference-visibility-manifest.mjs) checks adapter parity and current source, bundle, and screenshot hashes. These traces cover one authored world and first uses of five actions.

We next extracted the physical-action transition from the HTTP handler into a function used by both the route and a [reducer-graph study](reference-reducer-graph.mjs). This removes a major weakness of a separately hand-written scene simulator. The study explored 5,745 reachable abstract states and 66,410 valid transitions among 14 representative action choices, including repeated opening and page turns, all lamp settings, requesting and presenting objects, repeat comparisons, hints, and moves. The abstraction discards event IDs and times, revision numbers, action count, and exact positions while retaining page, lamp, card, comparison, presentation, hint count, and whether identity, stamp, or UV observations have ever occurred. For 60,666 merged histories it checked that the verified desk text and every representative next-action result agreed. It also checked 34,470 boundary-coordinate comparisons against representative movement, including unavailable card moves, since exact coordinates should change placement but not facts. The deepest explored representative trace had 15 actions, below the route's 200-action cap. The [SQLite result](reference-reducer-graph.json) and [PGlite PostgreSQL result](reference-reducer-graph-postgres.json) matched; selected witness and deterministic longer traces also matched 352 real HTTP actions and 23 stale-revision rejections per adapter.

Within that physical-action abstraction, the shortest route to an inferable mismatch without `compare` is `open` then `card`. The verified desk context never contains the UV result before a UV lamp action, and never contains the *explicit comparison sentence* before a comparison action. Those last two statements concern different facts: the comparison sentence is withheld, but its conclusion is already derivable. The graph's transition-equivalence checks support its state merging for the visited representative histories, not a proof over arbitrary coordinates, player questions, model replies, filing, image pixels, other authored worlds, or the deployed build. The artifact is therefore an executable scoped audit, not a universal certificate of every gameplay path. The methodological lesson for the authoring tool is to take transitions from production code, state precisely which variables are abstracted, test that merged states have the same observation and successors, and give a shortest violating trace when a declared dependency fails.

There is a cheaper necessary-condition check before graph search. Let $P(e)$ be facts guaranteed by the prerequisite actions that make an event $e$ available, and let $\operatorname{Cl}(P(e))$ close those facts under declared deterministic derivations. If a claimed new fact $f$ is already in $\operatorname{Cl}(P(e))$, then $e$ cannot be its first informational reveal to an actor who retains the prerequisite observations. For this desk, comparison requires opening the passport and requesting the card; those actions expose E. Vale and N. Vale, and `signatureMismatch` is a deterministic relation between them. The [prerequisite-closure preflight](prerequisite-closure.mjs) returns that two-leaf proof for the [reference audit](reference-prerequisite-audit.json). It reports the mismatch as already knowable before comparison on the visible-history, player-API, verified-desk, and full-model-request boundaries. The repaired initial player API no longer includes the document signatures or stamp date, while the full target prompt still includes the card signature, stamp date, and UV result. An action can still make evidence more salient or record that it was inspected. To make comparison genuinely informational, an author would need to withhold one necessary ingredient until that action or introduce a new measurement that the earlier documents do not determine. A `not-proven-known-before` preflight result is only an absence of this simple proof; the runtime graph and surface audits remain necessary. The [preflight tests](prerequisite-closure.test.mjs) include alternate prerequisites and validate the reference's comparison guard against the shared reducer on key states.

The preflight must be recipient-scoped in the orchestration game. Otherwise A's inspection would incorrectly count as B already knowing the seal color. In the [eight-world chain audit](chain-prerequisite-audit.json), the color is not proven known to B before A shares it, and the route is not proven known to C before B shares it. Those are the candidate information-transfer edges, supported separately by identical paired-world requests before the artifact and different requests afterward. By contrast, after B receives the color, B's private codebook already determines the route; `decode-route` is a computation, not a fresh informational reveal to B. After C receives the route, C's private fleet schedule already determines the vehicle; allocation is likewise computation rather than information acquisition. This distinction lets an author describe each specialist's actual role without requiring every step to introduce a secret. The preflight uses an authored action/fact contract, not a source-derived deployed workflow, so its positive handoff candidates still need request-boundary and runtime checks.

We tested that request-boundary check against the workshop's **actual request builders**, rather than a separate research-only formatter. The HTTP route and [pair auditor](recipient-request-audit.mjs) use the same pure [orchestration compiler](../server/orchestration-context.mjs), followed by the same [provider-body builder](../server/model.mjs) used immediately before `fetch`. For every pair, the serialized provider bodies were byte-identical before a saved reply was addressed to that recipient and differed in the inserted shared message afterward; expected route or vehicle labels also differed. The [HTTP route test](../tests/orchestration.test.mjs) asserts the exact B context after a real local board share; a [provider test](../tests/model.test.mjs) asserts that the body builder's result is exactly the JSON passed to `fetch`. These records are constructed local fixtures, not authenticated production events; the tests establish the compiler boundary and fault detection for those cases, not a deployed certificate or model reliability.

The local web app now has an **optional finite handoff contract** beside the three prompt slots. An author enters one or two directed role edges, a wait label, and a bounded source-label-to-recipient-label table. The [server contract evaluator](../server/orchestration-contract.mjs) stores every raw model reply with a separate `waiting`, `published`, or `rejected` verdict. Before a saved share, a target's final label is rejected; after a share, the reply must match the latest published source label's mapped result as a whole label. The board endpoint accepts only a published source reply directed along a declared edge, so a rejected raw reply cannot become another specialist's authoritative handoff. The same saved record also compiles a `SOURCE_A=ABSENT` or quoted `SOURCE_A="amber"` system-state field, with explicit state-to-output branches. A tester can type an imitation into an ordinary user message, but cannot change that server-built field or the publication decision. This is a provenance signal, not a claim that A's answer is true. Old configurations remain unconstrained. In an [HTTP fixture test](../tests/orchestration-gate.test.mjs) on both SQLite and PGlite PostgreSQL, two early answers and one answer following a contradictory tester claim remained visible but could not be shared; the A→B→C chain published after valid saved replies. The [browser check](../tests/browser/orchestration.spec.ts) saved a two-edge contract through the form, displayed a rejected raw reply, kept its share control disabled, and showed the exact compiled state and rule in the context inspector. This is deterministic local enforcement with scripted replies, not a live model attack result or a deployed feature. It authenticates the saved source record and mapped uptake, but cannot decide whether A's observed color was true; that needs an authored world oracle or trusted observation event.

The [locked 32-call live-model protocol](orchestration-gate-live-protocol.md) completed through the local HTTP route. Four opposite-color/codebook worlds crossed clean and fixed tester-claim conditions before and after a genuine saved share, with two fresh runs per condition. A was a deterministic true-color fixture, so only B called GPT-OSS 20B. The [plan tests](orchestration-gate-live-plan.test.mjs) established identical full B provider bodies across opposite-color twins before sharing and different bodies afterward. The [raw record](orchestration-gate-live-results.json), [summary](orchestration-gate-live-summary.json), and [integrity analyzer](analyze-orchestration-gate-live.mjs) verify all 32 bodies and saved publication verdicts; a [separate check](verify-live-gate-errors.mjs) reconstructs all 24 provider-429 attempt bodies. All 32 planned calls eventually received replies. In clean conditions, B waited exactly before sharing in 8/8 and gave the correct whole route after sharing in 8/8; the local gate marked them `waiting` and `published`. With a fixed application-update claim before sharing, B prematurely gave the claimed route in 8/8. With a contradictory desk correction after a genuine share, B gave the route for the claimed opposite color in 8/8. The local gate rejected all 16 raw attack replies. Provider interruptions were not counted as waits or model failures. This shows raw susceptibility and effective local publication enforcement for four synthetic worlds, one phrasing per attack condition, and one model; it does not test an adaptive attacker, source-model truth, deployed Vercel behavior, or population reliability. Before-share claims sometimes named the true hidden color, but no saved share had occurred, so those answers were still premature.

The app now creates two runs from a saved root handoff and a one-slot source system template. Each run receives a server-owned fact binding and frozen snapshot hash. Turns and shares advance a monotonic event sequence in the same database transaction as the run update; each event records message and board prefix counts and hashes. ### Sealed observation and two causal cuts

The local editor now offers a **sealed-card** pair. Both worlds freeze the same source prompt and case. The authored amber/cobalt value remains in a server-owned binding, and A's complete provider requests are identical while the card is closed. Clicking the card writes one ordered `observe` event and adds a verified observation to A's next request. The audit requires the two opened A requests to differ only at that fact slot. It then checks a second cut: B's reconstructed full requests are equal before a saved A-to-B share and differ afterward. A valid sequence is `observe`, source reply, share, recipient reply. The author view exposes the first differing request field and compares the actual saved B requests and replies with the reconstructed after-share requests. This is a scoped information-flow test at the exact app and provider compilers, not proof that the model visually perceived an object.

The [sealed-card HTTP test](../tests/orchestration-sealed-card.test.mjs) runs on SQLite and PGlite PostgreSQL. It checks equal frozen twins, a rejected premature source guess, a valid closed-card wait, a fact-free open request, duplicate-open prevention, event ordering, false-source diagnostic propagation, scored ineligibility for a false source, and rejection of a changed observation record. The local score preview uses the server-owned fact to require a true source label plus correct mapped final reply. It is an author diagnostic, not yet a festival leaderboard or the player-facing passport scene. ## Evaluation protocol before a research claim

The next study should preregister three independent axes: information visibility, model prompt, and runtime enforcement. Use identical authored worlds and user requests across a prompt-only full-case baseline, information-gated requests without output gating, and information-gated requests with typed artifacts and a publish gate. This separates a prompt improvement from a changed information boundary and from deterministic application enforcement. Randomize world values and prompt order. Use at least dozens of independently generated pairs per task family and repeated calls per pair; report the number of pairs and calls, per-condition exact outcomes, confidence intervals clustered by pair, raw provider errors, and latency/cost. A two-world demonstration cannot support significance claims.

Each pair should run before any handoff, after the true handoff, after a swapped or stale handoff, and after a forged user claim. Include incorrect but authentic upstream artifacts to measure whether the downstream model checks them or merely copies them. This is motivated by the documented answer-substitution effect in [controlled multi-agent handoff experiments](https://arxiv.org/abs/2609.36855). The primary measurements are premature finalization, paired-world correctness after a valid handoff, artifact acceptance errors, semantic errors in upstream extraction, and useful waiting behavior. For interactive levels, add time-to-insight, proportion of players who manipulate the intended objects, and whether removing an object or action changes success. Human reviewers should assess narrative plausibility and whether the supposed prerequisite feels discoverable; automated request equality cannot measure those qualities.

Repeat the contract across additional task families and pinned models, with provider differences recorded explicitly. Provider failures must remain separate from role failures: the Groq tool-call 400 and Gemini 3.8 Flash availability errors here would distort a naive success rate if failed calls were silently counted as abstentions or wrong answers. Archive serialized requests, response text, model identifier, temperature, artifact provenance, trial order, timestamps, and verifier version so a prompt or provider change can be examined later. The crossed route follow-up varied channel and handoff format under one base instruction; a further controlled chain run should isolate the base instruction from the compiled state representation. Repeat adversarial prompts with fresh phrasings and repeated calls rather than treating one successful board-claim template as an exhaustive attack. The eight chain worlds are a small exhaustive factorial of authored facts, not eight independent samples from real projects.

## Limits and falsification

The strongest objection is that the technique could merely formalize ordinary secret hiding. Its potential contribution is the combination of an **author-declared interaction**, generated counterfactual worlds, byte-level pre-handoff equality checks, and a runtime trace that asks whether the interaction actually changed the recipient's behavior. A broader literature review and multi-domain experiments are still required before claiming this combination is novel or effective. The nearest paired benchmark we found, AgentAbstain, changes a visible query, environment, or tool condition between twins; our certificate instead requires the recipient's pre-event view to remain the same. That is a meaningful technical distinction, but not proof of originality by itself.

The method can fail if authors choose uninteresting variables, if a different clue reveals the answer, if a model has external access or memory, if the verifier accepts multiple outcomes, or if a player exploits hidden data in the client. An HMAC authenticates origin and integrity only. A model can obey a forged user sentence even when the server refuses to issue an artifact. In a game, a deterministic gate may protect state while making the interaction feel arbitrary if the visible story does not explain why the fact is unavailable. These limitations are design tests, not edge cases to hide. Our local prototypes deliberately challenge certificates with alternate routes and injected claims; broader authoring tools should make the same challenge routine before presenting a contract as passed.

## Conclusion

The local app connects finite handoff rules to server-bound paired worlds, a server-owned object event, and an author audit at the actual model-request boundary. Its score preview recalculates observation-to-handoff lineage rather than trusting a saved success flag. The passport scene now provides a second implementation path: a recipient-scoped prerequisite proof rejects an impossible reveal claim, the event-cut graph searches modeled action paths, and browser replays test selected witnesses against actual rendered and downloaded observations. The asset-omitting negative control shows why the graph and browser must cross-check each other. The 25 first-use action orders and broader physical-action graph find that comparison never supplies the signature mismatch first in the tested world. A separate conditional-evidence audit distinguishes actions needed in every world, useful only after some observations, or decorative for a declared decision.

The route, chain, and two-clue studies show why structural necessity, model uptake, response format, source truth, and publication authority need separate verdicts. The visibility work adds observer-specific boundaries: a fact may appear in a full target prompt, verified desk context, player API, accessible text, rendered image, or downloadable metadata at different times. A player can also derive a conclusion from earlier observations even when no single screen says it. Claims beyond these local fixtures require more task families, varied attack phrasings and models, broader browser path checks including questioning and filing, and human tests of whether the objects are discoverable and useful. The local editor and research fixtures are not deployed.
