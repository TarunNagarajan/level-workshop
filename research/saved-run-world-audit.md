# Auditing saved handoffs against a world fact

The [saved-run auditor](saved-run-world-audit.mjs) joins two actual local HTTP test runs to two world bindings. The binding records a run ID, the frozen snapshot hash, the private fact that the source specialist should report, and a source system-prompt template with exactly one `{{FACT}}` slot. The original research harness supplied those bindings. The app now creates paired runs and their bindings together in its own database, then loads them inside an author-only audit route. A client-supplied binding is not used by that route.

For each world, the auditor finds the latest addressed share and its saved, published source reply. It checks the source reply against the bound world fact. It also reconstructs the source's provider request from its saved context, verifies that the system prompt exactly equals the trusted template rendered with the world fact, and checks that the two full source requests become identical when restored to that template. This proves that the source request carried the declared fact in these two runs without treating an incidental substring as a fact slot. It does not prove the model attended to it.

The recipient check reuses the app's [context compiler](../server/orchestration-context.mjs), [provider-body builder](../server/model.mjs), and [pair auditor](recipient-request-audit.mjs). The complete recipient provider bodies must be identical across the two worlds before the saved share, different afterward, and associated with different correct mapped outcomes. The result keeps request necessity, source request exposure, source truth, and binding validity separate rather than reducing them to a single pass badge.

The [HTTP test](saved-run-world-audit.test.mjs) creates the two worlds through the real orchestration routes and reads the saved runs back. A true amber/cobalt pair passes on SQLite and PGlite PostgreSQL. In a second pair, the source gives the opposite color in each world. Both replies are saved, published, and shared through the app. The recipient request dependency still passes, but source truth fails in both worlds. B then returns the route implied by each false source value, and the current local gate publishes both wrong-world routes. A third control gives A no seal fact at all while the scripted replies happen to match the two worlds. Recipient necessity and source correctness pass, but source request exposure fails. Another control changes an unrelated source instruction; a stale run binding and wrong model also fail. These cases demonstrate why a correct-looking output, a valid board link, source access, source truth, and a real recipient dependency are distinct claims.

The audit covers one root A-to-B handoff, finite whole-label facts, and the exact provider-body compiler. Without an event log, a later recipient turn returns `inconclusive-stage`. The app now commits a monotonic event number and prefix hashes with each turn or share. With the saved event log, the auditor reconstructs the share boundary after later turns and returns `invalid-checkpoint` if counts, order, or hashes disagree. The [server-bound HTTP test](../tests/orchestration-world-pairs.test.mjs) passes on SQLite and PGlite PostgreSQL. The [browser test](../tests/browser/orchestration.spec.ts) creates a pair, shares both source replies, and reads the request audit in the editor. These are local scripted checks, not a deployed or human usability result. The prompt-injected pair has no object event. The sealed-card pair below adds one server-owned observation, while the fact remains authored at pair creation. Neither mode covers every reachable history.

## Production record shape

The current root-source pair stores two authored fact values, frozen snapshots and hashes, the source template, observation mode, and the provider base URL. Pair creation is one database transaction. In sealed-card mode, the frozen snapshots are identical and the author sees a covered card until its run is opened; the source model receives the fact only after that event, and the recipient model gets it only after a declared share. A scored game would need an immutable world revision linked to the level version, with the hidden fact withheld from player endpoints. Reject an audit whose run, model, or snapshot hash does not match its saved binding.

The current orchestration stream numbers turns, sealed-card observations, and board shares. It records the source reply and board entry IDs, plus prefix counts and hashes; the model reply keeps its reconstructible request context and publication verdict. Each run mutation and event entry commits in one transaction. The share checkpoint reconstructs before and after recipient requests without guessing from timestamps. In sealed-card mode, the auditor requires the observation before the saved source turn and verifies its fact against the server binding. It reconstructs identical source requests before the observation and a one-slot difference after it. The current `dispatch-seal` is an author-lab object with one open action; richer scene tools and player-visible surfaces still need their own audit. Prefix hashes detect inconsistent app records, but are not tamper-proof against a database administrator who can rewrite both records and hashes.

The author view now shows request necessity, source request exposure, source agreement with the authored world fact, the first differing request field, and actual saved recipient uptake separately. The detailed API result retains full-body contrasts and hashes. A world whose source reply is wrong remains useful as a diagnostic run; its raw text and saved board attempt remain visible to the author. In sealed-card mode, the source publication carries `sourceTruth` and `scoreEligible`, later mapped replies inherit eligibility, and the score preview rejects an otherwise consistent wrong-world completion. This preview does not itself award player points. One correctly mapped recipient reply is an observed uptake for that run, not a reliable estimate of model behavior.

The preview now recalculates eligibility through the [score verifier](../server/orchestration-score.mjs) rather than trusting those stored flags alone. It requires a matching frozen snapshot, a complete [event ledger](../server/orchestration-event-ledger.mjs), exactly one matching sealed-card observation, a true source reply whose provider context contains the verified fact, and each ordered share and finite mapping through the final role. A prompt-injected pair stays diagnostic even if A and B answer correctly, since no object was opened. In the [HTTP test](../tests/orchestration-sealed-card.test.mjs), changing a saved observation event after a successful run turns that run's preview diagnostic while the untouched twin stays eligible. The [A-to-B-to-C test](../tests/orchestration-score.test.mjs) exercises a two-share chain. These checks are local application consistency and authored truth checks; the prefix hashes are not tamper-proof administrator signatures, and no player points are awarded.

For author testing, retain an explicit diagnostic path through the downstream roles. A false but authentic A reply is valuable evidence about whether B and C blindly propagate a mistake. Mark that share as diagnostic and carry its failed world-truth status through later derived replies; none of those replies should count as a scored success. The ordinary player path should require both a valid saved lineage and a true source observation. This separates permission to run an experiment from permission to publish its outcome as a successful level completion.

The [sealed-card HTTP test](../tests/orchestration-sealed-card.test.mjs) exercises that distinction on SQLite and PGlite PostgreSQL. It also checks that opening ignores a client-supplied fact, cannot be repeated, and leaves the saved observation in the required order. A locked [six-call live transfer](sealed-card-live-v2-protocol.md) with GPT-OSS 20B yielded two exact pre-open waits, two true source labels after opening, and two correct mapped recipient labels after sharing. The [raw record](sealed-card-live-v2-results.json) and [analyzer](analyze-sealed-card-live-v2.mjs) match all six full request hashes to the saved audit, with both score previews eligible. An earlier [locked attempt](sealed-card-live-protocol.md) stopped after the first post-open request returned HTTP 400; a [four-call ablation](sealed-card-prompt-ablation.md) associated that error with a prior wait sentence in A's prompt, so the completed transfer used a fresh preregistered simplified prompt. These are small synthetic engineering checks. The recipient before-share comparison is a reconstructed request boundary, while the after-share uptake is an actual model call.

In a separate [four-call fixed claim challenge](sealed-card-adversarial-protocol.md), two unopened A calls ignored a user's false-open claim and waited, and two B calls ignored an opposite-color desk claim after true source fixtures were shared. The [record](sealed-card-adversarial-results.json) and [analyzer](analyze-sealed-card-adversarial.mjs) verify the request hashes. None of these four calls produced a raw violation, so they do not demonstrate live gate rejection. The neutral-question pair audit establishes the structural handoff boundary for that pair; its reconstructed after-share hashes do not match the world-specific attack questions, and the analyzer checks this distinction explicitly.
